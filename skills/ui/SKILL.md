# gdm:ui — 스크린샷 기반 화면 수정 루프

## 역할

스크린샷·화면 피드백을 받아 원인 컴포넌트를 특정하고, 수정 결과를 시각 증거로
확인한 상태로만 끝내는 UI 실행자.

## 제약

- NEVER: 시각 확인 없이 "고쳐졌다"고 보고하지 않는다. 직접 확인(브라우저·
  시뮬레이터·스크린샷 도구)이 가능하면 직접, 불가능하면 사용자 확인을 받고
  그 기록을 증거로 남긴다.
- NEVER: 요청받지 않은 화면 요소를 함께 "정리"하지 않는다. 잘린 모달을 고치는
  작업에 버튼 색 통일이 따라오면 안 된다.
- NEVER: 새 스타일 값을 임의로 발명하지 않는다. 프로젝트의 기존 디자인 토큰·
  공통 컴포넌트·간격 체계를 먼저 찾아 재사용하고, 없으면 요청 범위에 필요한 값을
  정의하고 렌더로 검증한다. 일반적인 구현 선택만으로 별도 승인을 기다리지 않는다.
- IMPORTANT: 개방형 요청("이쁘게", "촌스러워")은 바로 구현하지 않고
  gdm-design으로 전환해 Claude Design용 프롬프트를 사용자에게 전달한다. 사용자가
  claude.ai/design에서 생성 완료를 확인한 뒤에만 DesignSync로 pull하며 Chrome 제어로
  대신 실행하지 않는다. `HTTP 429`, `rate_limit`, `quota exceeded`, 사용량 한도가
  명확할 때만 진행자 fallback을 허용한다.
- IMPORTANT: 구체적 웹 UI 수정의 런타임 확인은 실행 URL과 지원 터미널이 있고
  실행 중인 `terminal-browser`가 있으면 gdm-go 스킬의
  `terminal-browser-background-tab.sh open <url>`로 비활성 AI 탭을 만들고 반환된 browser와
  tab을 모든 `terminal-browser action -- snapshot|click|fill|eval`에 명시한다.
  이는 프로젝트 자동 테스트와 스크린샷 증거를 대체하지 않으며, 도구가 없으면 기존
  브라우저·시뮬레이터·사용자 확인 흐름으로 폴백한다.
- IMPORTANT: 자동 확인은 `terminal-browser open`, `--split`, `--follow`를 사용하지 않고
  완료·실패 때 `terminal-browser-background-tab.sh close <key> <id>`로 AI 탭을 정리한다.
  사용자가 화면 표시를 명시적으로 요청한 경우만 대화형 open 절차를 별도로 사용한다.
  실행 중인 terminal-browser가 없으면 새 화면을 만들지 않고 기존 headless 흐름으로 폴백한다.

## 프로세스

1. 문제 특정: 스크린샷·설명에서 어느 화면, 어느 컴포넌트, 어느 상태(호버·
   스크롤·특정 데이터 길이)인지 좁힌다. 재현 조건이 불명확하면 그것부터 묻는다.
   기존 체계 안의 구체적 시각 결함이면 이 루프를 계속하고, 새 미학·레이아웃 방향을
   고르는 개방형 시각 변경이면 gdm-design으로 전환한다.
2. 코드 추적: 해당 화면의 컴포넌트·스타일 정의를 실제로 열어 원인을 찾는다
   (전역 스타일 vs 로컬, 부모 레이아웃 제약 여부).
3. 수정: 기존 체계(토큰·공통 클래스) 안에서. 같은 원인이 다른 화면에도 있는지
   한 번 확인하되, 수정 범위는 요청 화면으로 한정하고 나머지는 보고만 한다.
4. 확인: 수정 후 화면을 직접 보거나 사용자 확인을 받고, 그 기록(스크린샷 또는
   문답)을 남긴다 — gdm 작업 안이면 `.gdm/<슬러그>/ui/`에 저장해
   `gdm pass --manual`의 증거로 쓴다. 잘림·겹침 수정은 긴 텍스트·좁은 화면
   같은 경계 조건에서도 확인해야 완료다. 웹 UI이면 terminal-browser로 정상·경계 상태의
   실제 상호작용을 우선 재현하고, 기계 판정 가능한 assertion은 gdm check 명령에 포함한다.

## 엣지 케이스

- 스크린샷만으로 어느 화면인지 특정이 안 되면: 추측으로 고치지 말고 URL·메뉴
  경로를 묻는다.
- 원인이 공통 컴포넌트라 수정 파급이 여러 화면이면: 파급 범위와 회귀 검증을 알리고
  승인된 수정 범위에서 진행한다. 요청과 관계없는 동작 변경이나 별도 제품 결정이
  필요할 때만 질문한다. 기존 승인을 다시 묻지 않는다.

## 출력 형식

수정 보고는 "무엇이 문제였고(원인 컴포넌트:라인) → 무엇을 바꿨고 → 어떻게
확인했는지" 세 줄이 기본. 개방형 요청은 gdm-design의 프롬프트 handoff 출력 형식을 따른다.

## 예시

Bad — 확인 없이 완료 주장 (하지 말 것):

```
padding을 16px로 늘렸으니 이제 안 잘릴 겁니다. 완료했습니다.
```

"안 잘릴 겁니다"는 추측이다. 화면을 봐야 완료다.

Good:

<example>
사용자: [스크린샷] 모달 밑이 조금 잘립니다. $gdm-ui

어시스턴트:
1. "확인: 심의 상세 모달, 항목이 6개 이상일 때 하단 버튼이 뷰포트 밖으로 —
   원인은 ReviewModal.vue:88의 고정 height"
2. max-height + 내부 스크롤로 수정 (공통 모달 컴포넌트의 기존 패턴 재사용)
3. "항목 3개/10개 두 케이스 확인했습니다 — 스크린샷: .gdm/fix-modal/ui/c2.png.
   같은 고정 height가 ExportModal에도 있는데 이번 범위 밖이라 보고만 합니다."
</example>
