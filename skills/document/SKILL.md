# gdm:document — 요구사항 추적형 문서 작성

## 역할

여러 출처의 요청을 빠짐없이 추적해 사람이 계속 편집할 수 있는 문서로 구성하고,
내용·형식·최종 상태를 검증한 뒤 발송 가능한 파일을 전달한다.

## 형식 라우팅

- DOCX 작성·수정은 설치된 `documents` 계열 스킬의 생성·렌더·검증 절차를 함께 따른다.
- PDF 자체를 만들거나 읽을 때는 `pdf`, 발표자료는 `presentations`, 표 계산이 중심인
  워크북은 `spreadsheets` 스킬을 함께 사용한다.
- 사용자가 내용 초안만 원하면 파일을 만들지 않고 구조화된 텍스트를 제공한다.
- 재사용 템플릿 제작 요청은 `template-creator`로 전환한다.

형식 스킬은 파일 조작을 담당하고, 이 스킬은 요구사항 추적·내용 구조·발송 상태 판정을
담당한다.

## 제약

- NEVER: PDF 페이지나 스크린샷을 Word 본문에 통째로 붙여 "별첨 작성"으로 처리하지
  않는다. 제목·문장·표·코드 블록을 네이티브 문서 요소로 재작성한다. 원형 보존이
  명시적으로 필요하면 원본 PDF를 별도 첨부하거나 이미지 부록임을 분명히 한다.
- NEVER: 열어보지 않은 소스의 내용, 메모, 변경 추적을 반영했다고 주장하지 않는다.
- NEVER: 요구사항 대조 없이 "모두 반영" 또는 "발송 가능"을 선언하지 않는다.
- NEVER: 원본 파일을 명시적 요청 없이 덮어쓰지 않는다. 작업본과 최종본 경로를 구분한다.
- NEVER: 의료·법무·재무 등 도메인 규칙을 출처 없이 보완하거나 추측하지 않는다. 기존
  문구와 실제 구현이 충돌하면 어느 쪽을 채택했는지와 확인 필요 사항을 남긴다.
- IMPORTANT: 검토본은 변경 추적·메모를 보존하고, 발송용 최종본은 사용자의 의도에 따라
  변경을 수락하고 메모·숨은 수정 흔적을 정리한다. 두 상태를 섞지 않는다.
- IMPORTANT: 본문에 필요한 이미지는 유지할 수 있지만, 이미지 안의 텍스트가 핵심 요구사항이면
  검색·복사·수정 가능한 본문으로도 제공한다.

## 프로세스

### 1. 입력과 완료 조건 확인

요청문, 메일 본문, 메모, 첨부파일과 기존 문서를 실제로 읽고 다음을 확정한다.

- 독자와 문서 목적
- 원하는 형식과 저장 위치
- 검토본인지 발송용 최종본인지
- 유지해야 할 기존 레이아웃·표·이미지
- 추가·수정·삭제 요청

사소한 누락은 합리적으로 가정해 진행하되, 문서 방향이나 법적·운영 의미를 바꾸는 선택은
사용자에게 확인한다.

### 2. 반영표 작성

작업 전에 내부 반영표를 만든다.

| 요구사항 | 출처 | 반영 위치 | 검증 방법 | 상태 |
|---|---|---|---|---|
| 요청 문구 | 메일/메모/파일 | 절·표·별첨 | 텍스트/구조/렌더 검사 | 대기 |

사용자에게 표 전체를 매번 보여줄 필요는 없지만, 최종 판정은 이 표를 기준으로 한다.
상충하는 요청은 조용히 합치지 말고 우선순위와 채택 근거를 기록한다.

### 3. 구조와 내용 작성

1. 결론과 핵심 요약을 앞에 두고 독자가 필요한 순서로 개요를 잡는다.
2. 기존 문서를 수정할 때는 스타일·용어·번호 체계를 먼저 확인하고 재사용한다.
3. 표는 비교·매핑·규칙에, 흐름도는 실제 순서·주체·데이터 이동에만 사용한다.
4. 별첨은 본문에서 참조 가능한 번호와 제목을 붙이고 독립적으로 읽히게 작성한다.
5. 기술 문구는 실제 코드·API·운영 설정과 대조할 수 있으면 대조한다. 원문과 구현이
   다르면 최종 문구와 이유를 반영표에 남긴다.

### 4. 네이티브 편집 가능성 확인

- 제목은 제목 스타일, 설명은 문단, 정형 데이터는 실제 표로 만든다.
- XML·JSON·명령어는 텍스트 코드 블록으로 만든다.
- 구조도는 가능하면 도형·표·연결선 등 편집 가능한 요소로 구성한다.
- 장식용 이미지를 제외한 핵심 문구가 이미지에만 남아 있지 않은지 확인한다.

### 5. 내용 검증

반영표의 각 항목을 문서에서 다시 찾아 상태를 완료로 바꾼다. 특히 다음을 검사한다.

- 요청된 절·별첨·표와 필수 문구가 존재하는가
- 이전의 잘못된 문구가 남아 있지 않은가
- 파일명, 날짜, 버전, API 이름, 수치가 서로 일치하는가
- "현재 방식"과 "향후 대안"처럼 상태가 다른 내용을 구분했는가
- 민감정보와 내부 로그·접속정보가 불필요하게 노출되지 않았는가

### 6. 파일·레이아웃 검증

형식별 스킬의 렌더링 절차를 실행하고 모든 페이지를 직접 확인한다.

- 잘림, 겹침, 빈 페이지, 표 머리글 고아, 제목만 남은 페이지가 없는지 확인한다.
- 문서 텍스트가 검색·복사되는지 확인한다.
- 이미지 개수와 용도를 검사해 원치 않는 페이지 스크린샷이 없는지 확인한다.
- 발송용이면 변경 추적, 메모, 주석 앵커, 숨은 변경 노드가 0인지 검사한다.
- 최종 파일을 다시 열고 예상 페이지 수와 필수 문구를 확인한다.

레이아웃을 보지 못했으면 "검수 완료"라고 하지 않고 `렌더 미확인`을 명시한다.

### 7. 전달

최종 보고는 다음 순서로 짧게 제공한다.

1. 완성된 파일과 저장 위치
2. 추가·수정된 절 또는 페이지
3. 반영표 미완료 항목과 확인 필요 사항
4. 실행한 검증과 결과

동봉할 메일 문구까지 요청받으면 문서 검증 결과와 정확한 파일명을 넘겨
`$gdm-email` 절차로 작성한다.

## 완료 기준

- 반영표의 필수 항목이 모두 완료다.
- 핵심 내용이 네이티브 문서 요소로 편집 가능하다.
- 렌더된 모든 페이지를 확인했다.
- 검토본/최종본 상태가 요청과 일치한다.
- 사용자가 지정한 경로에 최종 파일이 존재하고 다시 열린다.

하나라도 충족하지 못하면 완료가 아니라 미확인 또는 차단 상태로 보고한다.
