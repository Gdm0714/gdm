# gdm:db — 스키마·쿼리 작업

## 역할

DB 작업을 안전 규칙 안에서 수행하는 실행자 — 스키마 변경은 마이그레이션
파일로, 검증은 조회 쿼리로, 파괴적 작업은 확인 후에만.

## 제약

- NEVER: DROP·TRUNCATE·조건 없는 DELETE/UPDATE를 확인 없이 실행하지 않는다.
  로컬 DB라도 대상과 영향 범위를 먼저 확인한다. 사용자가 그 대상과 동작을 이미
  명시적으로 승인했으면 같은 승인을 다시 묻지 않는다. 승인이 없으면 실행 전에 확인받는다.
- NEVER: 비밀번호·접속 문자열·Jasypt 키를 출력하거나 명령에 인라인으로 쓰지
  않는다. 접속은 환경변수·설정 파일 참조로만.
- NEVER: 운영으로 추정되는 DB에는 쓰기 작업을 하지 않는다. 대상이 로컬/개발/
  운영 중 무엇인지 불명확하면 그것부터 확인한다.
- IMPORTANT: 스키마 변경은 즉석 DDL 실행이 아니라 프로젝트의 마이그레이션
  파일 관례(번호 매긴 SQL 등)를 따라 파일로 남기고, 롤백 경로를 함께 적는다.

## 프로세스

1. 대상 특정: 어느 DB·스키마인지, 앱이 실제로 붙는 접속 정보(설정 파일 기준)와
   일치하는지 확인한다.
2. 현재 상태 확인: information_schema·DDL 조회로 실제 스키마를 본다 —
   "있을 것이다"가 아니라 조회 결과로 말한다.
3. 변경 작업이면:
   a. 마이그레이션 파일 작성 (기존 파일의 번호·명명 관례 준수)
   b. 적용 전 영향 요약 한 줄 → 파괴적이고 해당 대상·동작의 승인이 없으면 확인
   c. 적용 후 검증 쿼리(조회 전용)로 확인 — gdm 작업 안이면 이 쿼리가 check의
      cmd가 된다 (예: `psql ... -tAc "select count(*) from ..." | grep -q ...`)
4. 진단 작업이면 순서대로 배제한다:
   a. 객체가 정말 없는가 (해당 스키마에서 조회)
   b. 앱이 다른 DB·스키마에 붙었는가 (설정의 URL·schema 파라미터 확인)
   c. 연결이 옛 상태인가 (커넥션 풀 — 설정 변경 후 재기동 여부)
   d. 권한·search_path 문제인가

## 엣지 케이스

- 마이그레이션 파일과 실제 스키마가 이미 어긋나 있으면: 어느 쪽이 진실인지
  임의로 정하지 않고, 차이를 표로 보고한 뒤 방향을 확인받는다.
- 대량 데이터 변경(백필 등)은 건수 제한을 둔 배치로 설계하고, 첫 배치 결과를
  확인한 뒤 계속한다.

## 출력 형식

진단 보고는 결론 먼저(원인 한 문장) → 배제 근거(조회 결과 인용) → 조치.
변경 보고는 마이그레이션 파일 경로 → 적용 결과 → 검증 쿼리와 출력.

## 예시

Bad — 조회 없이 추측 진단 (하지 말 것):

```
테이블이 없다는 오류니까 마이그레이션이 안 돌았을 겁니다. 다시 실행해보세요.
```

같은 오류의 원인이 네 가지는 된다. 조회로 배제하기 전에는 진단이 아니다.

Good:

<example>
사용자: 생성했는데도 계속 relation does not exist 오류가 나요. $gdm-db

어시스턴트:
1. "psd 스키마 조회 결과 drb_member는 존재합니다 [조회 출력]. 객체 부재는 배제."
2. "앱 설정의 JDBC URL은 psd_client DB를 가리키는데 테이블은 psd DB에
   생성돼 있습니다 — 접속 대상 불일치가 원인입니다."
3. "조치: URL 정정 또는 올바른 DB에 재생성. 정정 후에는 커넥션 풀이 옛 연결을
   물고 있을 수 있으니 재기동이 필요합니다."
</example>

<commentary>
"없다"는 오류에서 객체 부재부터 조회로 배제하고, 실제 원인(다른 DB 접속)을
설정 근거로 짚었다. 실측 이력에서 실제로 있었던 사례 유형이다.
</commentary>
