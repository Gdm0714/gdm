# UIUX 전문 역할과 협업 계약

## 목적과 적용 범위

화면을 제품의 목적에 맞게 아름답고 이해하기 쉽게 만들기 위한 책임 분담이다.
아래 11개는 논리적 역할이며, 항상 11명의 에이전트를 실행한다는 뜻은 아니다.
최종 방향과 의견 조정은 총괄이, 제품 코드 통합은 지정된 구현 담당 한 명이 맡는다.
이 문서는 `SKILL.md`의 디자인 계약·렌더 검증·독립 검수 계약을 확장한다.

- 새 제품이나 큰 리디자인은 UX 흐름, 타이포, 색을 최소한 별도 맥락에서 검토한다.
  동일한 검토자가 자기 설계를 다시 설명하는 것만으로 전문 검토를 대체하지 않는다.
- 작은 수정은 영향을 받는 역할만 활성화한다. 새 역할의 참여가 재설계 범위를 늘리지 않는다.
- 권장 동시 실행은 총괄 1명과 전문가 최대 3명이다. 런타임 상한이 더 작으면 따른다.
- 전문가의 기본 권한은 읽기와 제안이다. 같은 제품 파일을 동시에 수정하지 않는다.
- 총괄이 구현을 겸할 수 있다. 독립 시각 검수는 구현자의 자기검사와 구별한다.
- 색 개수, 폰트 종류, 카드 수, 장식 유무를 모든 제품에 적용되는 미적 금지로 만들지 않는다.
  선택 근거는 제품·사용자·정보·기존 체계에서 찾고, 실제 화면으로 결과를 판단한다.
- 제한된 자원이나 도구 때문에 수행하지 못한 역할·검증은 기록한다. 실행했다고 꾸미지 않는다.

## 모두에게 전달할 공통 브리프

전문가는 같은 대표 화면, 같은 데이터와 같은 최신 계약을 보고 판단해야 한다.
진행자는 다음을 자기완결적인 입력 묶음으로 제공한다.

1. 제품과 사용자: 누가 어떤 상황에서 무엇을 완료하려는가.
2. 이번 범위: 대상 화면·과업·플랫폼과 수정하지 않을 범위.
3. 성공 조건: 사용자가 알아차릴 정보, 취할 행동, 완료를 알 수 있는 신호.
4. 현재 근거: 화면과 상태별 렌더, 관련 코드·컴포넌트·토큰의 경로와 버전.
5. 실제 콘텐츠: 언어, 긴 제목, 숫자·단위, 항목 수, 이미지와 현실적인 빈 상태.
6. 디자인 방향: 기존 브랜드, 채택한 참고점, 제품 특유의 인상, 사용자 지정 사항.
7. 상태와 환경: 로딩·오류·완료·선택·초점, 작은 화면·확대·입력 방식·테마.
8. 구현 제약: 사용할 컴포넌트, 변경 가능한 토큰, 성능·플랫폼 제약.
9. 검증 여건: 볼 수 있는 이미지, 실행 가능한 렌더, 조작 가능 여부, 미확인 부분.
10. 결정 기록: 이미 합의한 사항과 아직 열려 있는 질문.

공통 브리프의 문체만 바꾼 보고서는 전문 검토가 아니다.
각 전문가는 자신의 관점으로 구체적 결함, 선택의 손익, 수정 위치를 찾아야 한다.

## 역할 배정표

작업 spec에 아래 표를 채운다. `역할`은 UIUX 책임이고 `실행 수단`은 도구 선택이다.

| 논리 역할 | 담당 또는 실행 수단 | 입력 버전 | 범위 | 산출물 | 상태 |
|---|---|---|---|---|---|
| 총괄·아트디렉터 | 진행자 | 브리프 버전 | 방향·통합 | 디자인 계약·결정 기록 | 예정/진행/완료 |
| 활성 전문 역할 | 담당 식별자 | 같은 렌더·계약 | 요소·상태 | 전문 검토 기록 | 예정/진행/완료 |
| 구현·디자인 시스템 | 단일 통합 담당 | 채택된 결정 | 소유 파일 | 코드·차이 기록 | 예정/진행/완료 |
| 독립 시각 검수 | 기존 검수 계약 | 구현 렌더 | 요구와 상태 | 결함·판정·한계 | 예정/진행/완료 |

비활성 역할은 이유를 짧게 남긴다. 예: 색을 바꾸지 않는 오타 수정.
담당 변경이나 계약 갱신 시 입력 버전을 함께 갱신해 이전 화면에 대한 의견이 섞이지 않게 한다.

## 1. 총괄·아트디렉터

- **책임:** 제품에 맞는 방향, 핵심 시각 요소, 전문가 간 충돌, 최종 우선순위를 결정한다.
- **관찰 질문:** 이 제품이어야 하는 이유가 화면에 있는가? 가장 먼저 보이는 것이 목표와 맞는가?
  각 부분을 합쳤을 때 하나의 제품으로 보이는가? 장식이 주요 정보를 밀어내는가?
- **산출물:** 디자인 계약, 대표 화면 선정, 채택·기각·보류와 이유가 담긴 결정 기록.
- **소유권 경계:** 전문가의 근거를 종합한다. 모든 의견을 섞거나 투표 평균으로 방향을 정하지 않는다.
- **통과 근거:** 대표 화면의 정보 계층과 시각 방향이 계약에 맞고, 미해결 충돌의 처리 결과가 남아 있다.

## 2. UX 흐름

- **책임:** 진입부터 탐색·행동·결과·복구까지 사용자가 목적을 달성하는 과정을 설계한다.
- **관찰 질문:** 다음 행동이 분명한가? 되돌아가면 입력이 보존되는가? 같은 정보를 다시 입력하는가?
  대기·승인 필요·완료를 구별할 수 있는가? 오류 뒤 할 수 있는 행동이 있는가?
- **산출물:** 핵심 사용자 시나리오, 상태 전이표, 불필요한 단계와 복구 흐름의 수정 제안.
- **소유권 경계:** 행동과 정보의 필요성을 결정한다. 구체 색상값이나 글꼴 취향을 대신 정하지 않는다.
- **통과 근거:** 정상·중단·실패 경로를 따라 목적을 완료하거나 명확하게 복구할 수 있다.

## 3. 정보 구조·레이아웃

- **책임:** 정보 우선순위, 그룹, 정렬 축, 밀도, 간격, 주요 행동의 위치를 설계한다.
- **관찰 질문:** 같은 목적의 정보가 모였는가? 제목·본문·보조 정보의 구획이 분명한가?
  카드와 구분선은 실제 그룹을 나타내는가? 공간이 줄 때 어떤 정보부터 재배치되는가?
- **산출물:** 정보 중요도 순서, 레이아웃 구조, 정렬·간격 규칙, 밀도별 배치 제안.
- **소유권 경계:** 공간과 그룹의 구조를 소유한다. 문구 의미나 타이포 규칙 변경은 해당 담당과 조정한다.
- **통과 근거:** 실제 데이터가 들어간 대표 화면에서 읽는 순서·그룹·주요 행동을 설명할 수 있다.

## 4. 타이포·가독성

- **책임:** 문자 크기·굵기·행간·줄 길이, 한글 줄바꿈, 숫자·단위, 긴 제목의 읽힘을 다룬다.
- **관찰 질문:** 본문과 보조 정보가 읽히는가? 강조가 많아 중요도가 평평해졌는가?
  줄바꿈이 뜻을 끊는가? 축약으로 꼭 필요한 내용이 사라지는가? 실제 폰트가 적용됐는가?
- **산출물:** 용도별 문자 스타일, 강조 단계, 줄바꿈·생략·숫자 정렬 규칙과 수정 위치.
- **소유권 경계:** 가독성을 확보한다. 공간 부족을 글자 축소로만 해결하지 않고 레이아웃 담당과 조정한다.
- **통과 근거:** 실제 언어·긴 콘텐츠·확대·작은 화면에서 핵심 내용을 읽고 구별할 수 있다.

## 5. 색·표면·테마

- **책임:** 배경·전경·강조·상태 색, 경계·그림자·표면 단계, 지원 테마의 관계를 설계한다.
- **관찰 질문:** 강조색이 행동과 정보의 중요도를 돕는가? 서로 다른 상태가 같은 색에 의존하는가?
  이미지 위 글자와 흐린 보조 글자가 읽히는가? 테마 변경 후 의미와 계층이 유지되는가?
- **산출물:** 의미별 색 토큰과 사용 쌍, 표면 단계, 상태·테마 조합과 검증할 대비 목록.
- **소유권 경계:** 색과 표면의 체계를 소유한다. 색을 잘 보이게 하려는 이유로 정보 우선순위를 바꾸지 않는다.
- **통과 근거:** 채택한 접근성 기준을 계산·점검하고 실제 렌더에서도 계층과 상태가 구별된다.

## 6. 비주얼 에셋·아이콘

- **책임:** 사진·일러스트·제품 이미지·아이콘의 목적, 스타일, 품질과 배치를 정리한다.
- **관찰 질문:** 이 자산이 정보나 제품 인상을 더하는가? 장식으로 빈 공간만 채우는가?
  아이콘만 보고 기능을 이해할 수 있는가? 선 굵기·크롭·해상도가 서로 어울리는가?
- **산출물:** 필요한 자산 목록, 실제 사용 위치, 아이콘·크롭 규칙, 출처·사용 조건 확인 기록.
- **소유권 경계:** 자산 제작·선정 제안을 담당한다. 읽기 전용 전문가는 파일을 생성하거나 교체하지 않는다.
- **통과 근거:** 실제 크기와 배경에서 의미·선명도·일관성을 확인하고 누락 자산을 명시한다.

## 7. 인터랙션·모션

- **책임:** 선택·초점·입력·끌기·로딩·완료 피드백과 상태 전환의 동작을 설계한다.
- **관찰 질문:** 동작이 무엇이 바뀌었는지 알려주는가? 입력을 막거나 화면을 흔드는가?
  완료 효과가 중간 응답에서도 반복되는가? 움직임 감소 환경에서 정보가 유지되는가?
- **산출물:** 요소별 상태표, 동작의 시작·종료 조건, 목적, 중단·반복·감소 모드 규칙.
- **소유권 경계:** 시각적 피드백과 전환을 담당한다. 업무 흐름이나 실제 완료 조건은 UX·구현 담당과 합의한다.
- **통과 근거:** 실제 상태를 유발한 기록으로 지연·중복·오해를 점검한다. 정적 이미지로 동작 통과를 선언하지 않는다.

## 8. UX 라이팅

- **책임:** 버튼, 입력 안내, 오류·빈 상태·확인 메시지의 표현과 용어를 통일한다.
- **관찰 질문:** 누르면 일어나는 일이 버튼에 드러나는가? 오류 이유와 다음 행동이 함께 있는가?
  내부 구현 용어가 노출됐는가? 긴 설명을 읽어야만 행동할 수 있는가?
- **산출물:** 상태별 최종 문구, 용어표, 의미를 유지한 짧은 표현과 보충 설명의 배치 제안.
- **소유권 경계:** 의미를 분명하게 표현한다. 문구를 줄이기 위해 실제 조건·비용·되돌릴 수 없음 등을 삭제하지 않는다.
- **통과 근거:** 실제 화면에서 문구와 동작이 일치하고, 처음 접한 사용자도 다음 행동을 이해할 수 있다.

## 9. 접근성·적응형 화면

- **책임:** 키보드·보조 기술·터치·확대·좁은 화면·긴 언어 등 다른 사용 조건을 검토한다.
- **관찰 질문:** 초점이 보이고 순서가 자연스러운가? 색 없이 상태를 이해할 수 있는가?
  확대 시 정보·행동이 사라지는가? 고정 영역이 내용을 가리는가? 터치와 키보드 모두 조작 가능한가?
- **산출물:** 환경·입력 방식별 점검표, 접근 가능한 의미·이름·순서, 재배치와 대체 조작 규칙.
- **소유권 경계:** 관련 담당에게 필요한 수정을 요구한다. 제품 구조를 임의 변경하거나 자동 검사만으로 통과시키지 않는다.
- **통과 근거:** 적용한 기준과 확인 방법을 명시하고, 자동 검출·실제 조작·미점검 범위를 분리한다.

## 10. 구현·디자인 시스템

- **책임:** 채택한 결정을 토큰·공통 컴포넌트·실제 상태와 데이터에 일관되게 구현한다.
- **관찰 질문:** 같은 의미가 같은 컴포넌트를 쓰는가? 화면마다 값이 갈라졌는가?
  선택한 폰트·자산·상태가 실제로 렌더되는가? 시안과 다른 부분은 의도된 것인가?
- **산출물:** 제품 코드, 토큰·컴포넌트 변경, 구현 제약과 계약 변경 기록, 렌더 근거.
- **소유권 경계:** 합의한 파일과 통합을 단독 소유한다. 다른 작업자의 변경을 되돌리거나 방향을 조용히 변경하지 않는다.
- **통과 근거:** 최신 구현에서 대상 상태를 재현한 근거가 있고, 계약과 차이가 있으면 이유와 처리가 기록돼 있다.

## 11. 독립 시각 검수

- **책임:** 구현자와 분리된 관점에서 실제 화면의 완성도, 일관성, 사용성 결함을 찾는다.
- **관찰 질문:** 시선이 의도한 순서를 따르는가? 반복 컴포넌트가 어긋나는가?
  어려운 데이터·상태에서도 유지되는가? 전문 보고서의 개선이 실제 화면에 반영됐는가?
- **산출물:** 위치·상태·증거·영향·심각도를 갖춘 결함 목록, 판정, 남은 검증 한계.
- **소유권 경계:** 기존 `run-auditor.sh` 계약과 독립성·권한 제한을 따른다. 임의의 협업 워커로 대체하지 않는다.
- **통과 근거:** 실제로 열람한 렌더·증거를 명시한다. 새 취향 제안과 요구 위반·사용성 결함을 구별한다.

## 실행 순서와 단계별 인계

### A. 구조 확정

총괄이 브리프와 대표 화면을 정하고 UX 흐름·레이아웃·UX 라이팅의 검토를 모은다.
핵심 과업, 정보 중요도, 실제 문구와 상태 목록을 먼저 정한다.
접근성에 구조적 제약이 있으면 이 단계부터 해당 역할을 참여시킨다.
시각 장식을 결정하기 전에 사용자가 무엇을 읽고 무엇을 하는지 설명할 수 있어야 한다.

### B. 시각 방향 구체화

타이포·색·에셋·인터랙션을 동일한 구조와 대표 화면에 대조한다.
동시 상한을 넘으면 순차 실행하며, 먼저 나온 결정과 아직 열린 질문을 다음 담당에게 전달한다.
전문가별로 독립적인 완성 시안을 만들어 합성하지 않는다. 하나의 방향 안에서 근거 있는 개선을 낸다.
불필요한 카드·배지·구분선·모션이 있으면 기능과 시각적 목적을 설명할 수 있는지 확인한다.
총괄이 충돌을 해결하고 구현 가능한 계약으로 통합한다.

### C. 구현

구현 담당 한 명이 채택된 결정을 적용한다. 전문가는 요청된 부분을 읽기 전용으로 재검토한다.
코드가 제약과 충돌하면 총괄에게 근거를 전달해 계약을 갱신하고, 임의로 절충하지 않는다.
동일 토큰·공통 컴포넌트는 하나의 정본을 유지한다. 다른 세션의 변경을 확인하고 보존한다.
테스트 추가·실행 권한, 로컬 화면 비간섭 규칙 등 상위 지침을 그대로 따른다.

### D. 실제 렌더 검수와 확장

동일한 데이터와 상태로 렌더하고, 대표 화면 전체와 문제 구간을 함께 확인한다.
정상 상태뿐 아니라 긴 텍스트·빈 상태·다수 항목·로딩·오류·작은 화면을 범위에 맞게 점검한다.
시각 전문가에게는 변경된 렌더를 제공한다. 코드나 토큰만 봤다면 코드·토큰 검토로 보고한다.
독립 검수가 요구되면 기존 검수 계약으로 진행한다. 결함을 고친 뒤 해당 상태를 다시 확인한다.
대표 화면에서 방향과 공통 요소가 정리되면 나머지 화면에 확장한다.
완료 조건 충족 뒤 근거 없는 취향 변경을 반복하지 않는다.

## 실행 수단과 권한

- `gdm role-run --role`에 허용되는 값은 `plan`, `analyze`, `review`, `audit`이다.
  UX·타이포·색 등은 전달하는 전문 관점이다. 이를 새로운 CLI 역할 이름으로 만들지 않는다.
- 계획에는 `plan`, 근거 분석에는 `analyze`, 변경 검토에는 `review` 등 실제 목적에 맞는 역할을 쓴다.
  `audit`를 단순 지정하는 것으로 `SKILL.md`의 독립 검수 실행 계약을 대신하지 않는다.
- 현재 런타임이 허용하면 네이티브 위임을 전문 검토에 사용할 수 있다.
  사용 전 해당 위임의 권한·상한과 입력 전달 방식을 확인한다.
- 도구가 없는 전문 러너에는 필요한 근거를 입력에 포함한다. 경로만 전달해 열람했다고 가정하지 않는다.
- 이미지 열람이 불가능한 러너는 구조·문구·토큰 검토만 할 수 있다.
  이미지 파일 경로나 해시를 받은 사실은 시각 검증의 증거가 아니다.
- 외부 자료가 필요하면 진행자가 허용된 경로로 확보한다. 비공개 코드·사용자 데이터·비밀을 전송하지 않는다.
- 독립 검수의 실행 수단·권한·모델·실행 트리 제약은 기존 계약을 따른다.

## 전문 역할용 공통 프롬프트

아래 템플릿의 빈칸을 채워 각 역할에 전달한다. 입력에 없는 화면을 추측해 평가하지 않는다.

```text
역할 이름: <위 논리 역할 중 하나>
목표: <사용자가 이 화면에서 달성할 일과 이번 개선 목표>
검토 범위(scope): <화면, 요소, 상태, 언어, 기기>
포함(in): <이 역할이 판단할 내용>
제외(out): <다른 담당의 소유 영역과 이번에 바꾸지 않을 것>
공통 기준: <최신 브리프, 디자인 계약, 기존 결정, 입력 버전>
근거(evidence): <실제로 전달한 이미지·텍스트·코드·토큰과 열람 가능 여부>
산출물(deliverable):
  1. 문제 위치와 상태
  2. 사용자 영향과 근거
  3. 구체적 수정안과 선택의 손익
  4. 관련 소유자·충돌·선행 결정
  5. 심각도와 확인 방법
  6. 미확인 사항 및 추가로 필요한 증거
제한(limits): 읽기 전용 제안. 파일 수정·도구 실행·재위임은 명시적으로 허용된 범위만.
다른 담당도 작업 중이다. 타인의 변경을 되돌리거나 소유 영역을 임의로 확장하지 말 것.
제품 목적과 무관한 개인 취향을 필수 수정으로 만들지 말 것.
실제로 보지 않은 렌더·수행하지 않은 조작을 확인했다고 말하지 말 것.
보고 형식: 위치 | 문제·영향 | 근거 | 권장 수정 | 관련 담당 | 심각도 | 확인 방법
```

## 통합 판단과 완료 보고

전문가의 의견은 숫자로 평균 내지 않는다. 총괄이 사용자 목적과 공통 계약으로 결정한다.
심각도는 과업 수행을 막는 문제, 반복되는 불편, 시각적 완성도 문제로 구별한다.
관찰 사실과 추정, 필수 수정과 선택 제안을 분리하고 채택하지 않은 이유도 남긴다.
완료 보고에는 참여 역할, 주요 결정, 실제로 확인한 상태, 남은 한계를 짧게 포함한다.
역할 수나 보고서 수 자체는 품질 근거가 아니다. 최종 화면과 사용 흐름이 판단 대상이다.
