# gdm:design — 전문 역할 분담과 통합 디자인

## 역할

진행자는 디자인 총괄이다. 사용자의 목표와 기존 디자인 체계를 읽고, 전문 역할의
의견을 하나의 방향으로 통합한다. 구현 소유자를 지정하고 대표 화면의 실제 렌더를
검토한 뒤 다른 화면으로 확장한다.

시작할 때 [DESIGN_ROLES.md](DESIGN_ROLES.md)를 읽고 역할을 배정한다.
역할은 총괄·UX 흐름·레이아웃·타이포·색·비주얼 에셋·인터랙션·문구·접근성·구현·
독립 검수의 11개 책임으로 구분한다. **11개 에이전트를 항상 실행한다는 뜻은 아니다.**
넓은 화면 설계·리디자인에서는 UX, 타이포, 색 검토를 별도 컨텍스트에 맡기고,
작은 수정에서는 필요한 역할만 활성화한다. 도구가 지원하지 않으면 역할별 자기검토로
진행하되 독립 전문가 검토를 수행했다고 보고하지 않는다.

총괄 포함 최대 4명 동시 작업을 권장하며 실제 런타임의 더 낮은 제한을 따른다.
전문가는 기본적으로 제안·검토를 하고, 토큰과 공통 컴포넌트는 지정된 구현 소유자가
통합한다. 각 의견의 채택·기각 이유를 기록한다. 서로 다른 시안을 부분적으로 섞지 않는다.
외부 디자인 도구나 사용자의 시안 생성을 기본 선행 조건으로 삼지 않는다.

## 제약

- NEVER: 디자인 계약 확정 전에 화면 코드를 쓰지 않는다. "일단 만들고 다듬자"가
  AI가 만든 것 같은 화면이 나오는 경로다.
- IMPORTANT: 직접 디자인이 기본이다. Claude Design은 사용자가 명시적으로 요청한
  경우에만 사용한다. 직접 진행하기 위해 외부 도구의 실패나 사용량 한도를 요구하지 않는다.
- NEVER: CLI의 `/design-sync`가 새 화면·레이아웃·프로토타입을 생성할 수 있다고 전제한다.
  DesignSync는 이미 존재하는 Claude Design 프로젝트와 컴포넌트 파일을 동기화한다.
- NEVER: Chrome 제어 스킬이나 브라우저 자동화로 claude.ai/design을 열어 프롬프트를 대신
  실행한다. 프롬프트를 사용자에게 전달하고 생성 완료 확인을 기다린다.
- NEVER: 명시적인 push 작업에서 DesignSync의 `finalize_plan` 전에 `write_files`나
  `delete_files`를 호출한다. 삭제 경로가 요청 범위를 벗어나면 실행하지 않고 보고한다.
- NEVER: 토큰에 없는 색·크기·간격 값을 코드에 넣지 않는다. 값이 더 필요하면
  토큰에 먼저 추가하고 쓴다. 이 규칙은 문서만으로 지켜지지 않는다는 것이
  실측이므로, 하드코딩 검사 check(아래 기계 게이트)로 뒷받침한다.
- NEVER: 렌더를 보지 않고 완료를 선언하지 않는다. 코드가 맞아 보이는 것은
  근거가 아니다 — 근거는 스크린샷이다. 렌더 수단이 없으면 "렌더 미확인"을
  명시하고 사용자 확인 기록을 증거로 받는다 (gdm-ui와 동일한 원칙).
- NEVER: 자동 도구 통과를 접근성 통과로 보고하지 않는다. 자동 검사는 위반의
  일부만 잡는다 — 통과 주장은 "자동 검출 위반 0건"까지만이고, 나머지는
  채점표와 라이브 점검이 커버한다.
- NEVER: 관성 목록(아래)의 선택에 자유를 쓰지 않는다. 그 선택이 주제에서
  도출된 이유를 계약에 적을 수 있을 때만 허용된다. 단 사용자가 콕 집어 요청한
  방향은 언제나 이긴다 — "사용자 지정"으로 기록하고 그 방향을 잘 해낸다.
- IMPORTANT: 프로젝트에 기존 디자인 시스템(토큰·테마·공통 컴포넌트)이 있으면
  새 방향을 발명하지 않는다. 기존 체계의 확장이 기본이고, 전면 리디자인은
  사용자가 명시했을 때만이다.
- IMPORTANT: 더미 텍스트(lorem) 금지. 실데이터가 없으면 현실적인 내용을 지어서
  채운다 — 카피도 디자인 재료다. 버튼은 무슨 일이 일어나는지 그대로 말한다.
- IMPORTANT: 사용자 화면을 방해하지 않는 headless·offscreen 검증을 기본으로 한다.
  현재 요청에서 허용하지 않은 창 활성화·입력 제어를 하지 않는다. 자동 테스트의 추가·
  실행 범위는 세션 지침과 사용자 승인에 따른다. 실행하지 않은 검사는 미확인으로 남긴다.

## 관성 목록 — 의도 없이 선택 금지

AI가 만든 화면이 수렴하는 조합. 하나라도 "그냥" 들어갔으면 채점표 6번에서 걸린다.
아래는 재검토 신호이며 특정 색·폰트·중립색의 보편적 금지 목록이 아니다.
제품 목적, 기존 체계, 사용자의 선택과 실제 렌더가 판단 근거다.

- 보라→파랑 그라데이션 히어로 / 크림 배경 + 세리프 제목 + 테라코타 액센트 /
  근검정 배경 + 네온 포인트 하나 — 세 가지 "안전한 룩"
- 모든 카드가 같은 radius + 같은 그림자로 나열, 모든 것이 중앙 정렬
- 이모지를 아이콘·섹션 마커로, 그라데이션 원·블러 도형을 채움재로 사용
- Inter·Space Grotesk를 "무난해서" 선택
- 제품의 표면·테마와 관계없이 고른 중립색 — 순수 회색 또는 색조가 있는 회색을
  실제 배경·글자·강조색의 관계로 판단한다
- 내용이 순서가 아닌데 붙는 장식 번호(01/02/03), 정보 없는 구분선

## 디자인 계약 — 두 층

**프로젝트 층 (영속 — 화면 간·세션 간 일관성 담당):**

- 정본은 문서가 아니라 **코드의 토큰 파일**이다: CSS 변수(`:root`/`.dark`)를
  시맨틱 이름 쌍(바탕/전경, primary/그 위 글자색)으로. 이미 있으면 그것이 정본.
- 의도 문서 `design-system.md`(30줄 이내): **구체 레퍼런스 1개**("1970년대
  강의 유인물", "공항 출발 전광판" — 형용사는 영역을, 레퍼런스는 점을
  특정한다), 톤, Do/Don't 몇 줄, 토큰 파일 경로. 길게 쓰지 않는다 — 문서는
  포인터이고, 준수는 기계 게이트가 강제한다.
- 단순한 화면의 출발점: 폰트 1~2개, 소수의 표면·모서리·그림자 단계.
  색은 바탕·전경·강조·상태 등 의미별로 정의한다. 브랜드색 개수와 접근성·상태용
  토큰 개수를 혼동하지 않는다. 고정 숫자나 장식 유무를 미적 완성도의 대용으로 삼지 않는다.
- 첫 실행이 이 층을 만들고(이때만 미학적 결정), 이후 실행은 확장만 한다.

**작업 층 (`.gdm/<슬러그>/design/spec.md`, gdm 밖이면 작업 폴더):**

이번 화면의 것만 — 컨셉 한 문장, **시그니처**(이 화면이 기억될 단 하나의
요소), 치수(문서형/에디토리얼), 레이아웃 요지, 디자인할 상태 목록(hover/
focus/비어있음/로딩/에러). **스타일 값은 여기 다시 적지 않는다** — 구조는
작업 층, 스타일은 토큰. 두 채널을 섞으면 화면마다 스타일이 갈라진다.

## 프로세스

기본 순서는 프리플라이트 → 공통 브리프·역할 배정 → 구조 검토 → 시각 검토 →
디자인 계약 → 대표 화면 구현 → 역할별 렌더 검토 → 통합·독립 검수 → 확장이다.
기존 화면 개선은 이미 확인된 문맥과 검증 수단을 재사용한다. 구현 선택만을 이유로
사용자에게 외부 시안 생성을 요청하거나 작업을 중단하지 않는다.

0. 프리플라이트: 이 환경에서 무엇을 검증할 수 있는지 먼저 확인하고 선언한다 —
   렌더 수단(playwright는 node 18+ 필요, 없으면 Chrome headless), 기계 게이트
   (axe·콘솔) 가용성. node는 기본 PATH만 믿지 말고 다른 설치본(homebrew·nvm)까지
   찾는다. 못 도는 게이트는 시작 시점에 대체 수단(계산식·스크린샷)과 함께
   선언한다 — "미점검"은 사후 고백이 아니라 사전 계획이어야 한다.
1. 맥락 수집: 로컬 디자인 토큰·공통 컴포넌트·대상 화면의 데이터와 상태를 읽는다.
   기존 Claude Design 프로젝트를 사용한다고 사용자가 알려줬으면 `/design-sync`로
   `list_projects` → `get_project` → `list_files` → `get_file` 순서로 원격 정본도 읽는다.
   목표 사용자·핵심 과업·실제 문구와 데이터·플랫폼·상태·제약을 공통 브리프로 묶는다.
   spec에 역할별 담당, 입력, 산출물, 쓰기 소유권, 검토 순서를 기록한다.
2. 치수 읽기: 문서형(도구·대시보드·관리 화면)인지 에디토리얼(랜딩·쇼케이스)
   인지 정한다. 문서형은 절제된 완성도, 에디토리얼은 관점 있는 미학 +
   과감함 한 곳(시그니처), 주변은 조용히.
3. 방향 선택: 제품·사용자·화면 목표, 실제 카피, 필요한 상태, 기존 토큰·컴포넌트 제약,
   반응형 폭, 접근성을 바탕으로 총괄이 방향을 정한다. UX·레이아웃·문구 역할이 먼저
   구조와 행동을 검토하고, 타이포·색·에셋·인터랙션 역할이 동일한 대표 화면을 구체화한다.
   접근성 역할은 구조와 시각 단계 모두 참여한다. 새 시스템이면 구별되는 후보 방향을
   비교해 하나를 선택하고, 기존 시스템이면 그 체계를 확장한다. 일반적 디자인 선택은
   총괄이 결정하며 사용자만 정할 수 있는 제품 결정만 묻는다.
4. 선택적 Claude Design handoff: 사용자가 이 도구를 명시적으로 요청했을 때만
   자기완결적 프롬프트를 전달하고 생성 완료 및 프로젝트 이름/ID를 기다린다.
   이 경우에도 브라우저 자동화로 프롬프트를 대신 실행하지 않는다.
5. 선택적 pull: 4단계의 사용자 생성 확인이 있을 때만 Claude CLI `/design-sync`로
   `list_projects` → `get_project` → `list_files` → `get_file` 순서로 지정 결과를 읽는다.
   접근 권한이나 프로젝트가 없으면 생성됐다고 추측하지 말고 필요한 조치를 알린다.
   직접 디자인 경로에서는 4~6단계를 생략한다.
6. 선택적 push: 사용자가 로컬 컴포넌트를 원격 디자인 시스템으로 올리는 양방향 동기화까지
   요청했을 때만, 쓰기·삭제 경로를 `finalize_plan`으로 먼저 확정한 뒤
   `write_files`/`delete_files`를 실행한다. 기본 디자인 생성·pull 흐름에서는 원격 쓰기를
   하지 않는다.
7. 계약 확정: 직접 선택한 방향 또는 받아온 산출물을 요청 범위·기존 변경과 대조한다. 프로젝트 층이 없으면 생성,
   있으면 확장. 자기검사 한 번 —
   "이 계약을 아무 주제에 냈어도 같았겠는가?" 그렇다면 그 부분이 관성이다.
   일반 크기 텍스트는 보조 문구·placeholder도 4.5:1, 큰 글자는 3:1을 기준으로
   토큰 쌍의 대비를 계산한다. 비텍스트 UI 대비는 별도 기준을 적용한다.
   직접 디자인은 작업 spec에 `designProvider: coordinator`를 기록한다. 선택적 외부
   디자인은 `designProvider: claude-design`과 원격 프로젝트·파일 식별자를 기록한다.
   지정된 구현 담당이 로컬 제품 코드를 작성·통합하며 기존 변경을 검토 없이 덮어쓰지 않는다.
   총괄이 구현을 겸하는 경우에도 소유자를 역할 배정표에 명시한다.
8. 구현: 시작 전에 이 스킬 디렉토리의 `CRAFT.md`(구현 미세 규칙 — 타이포·색·
   간격·상태·CSS 함정·카피)를 읽는다. 토큰만 사용하고, spec의 상태 목록을
   전부 만든다. 여러 전문가에게 같은 파일을 동시에 수정시키지 않는다.
9. 렌더 채점 루프: 대상 플랫폼의 좁은·중간·넓은 크기(웹 출발점 375/768/1440)와
   사용하는 테마로 스크린샷을 찍는다. 타이포·색·레이아웃 역할은 같은 렌더를 보고
   각각의 문제를 검토하고, UX·인터랙션 역할은 실제 조작 증거를 확인한다.
   전체 화면과 중요한 세부를 함께 본다. 채점표와 라이브 점검(아래)에 대조해 미달을 고친다.
   요구와 채점 기준을 충족하면 다음 단계로 진행한다. 추가 개선은 실제 결함이나
   미충족 요구가 있을 때 하며, 첫 채점 통과라는 이유만으로 재수정하지 않는다.
   전문가 의견은 위치·상태·사용자 영향·근거·권장 수정·확인 방법을 갖춰야 한다.
   취향 제안과 가독성·조작·일관성 결함을 구분하고, 미감과 사용성을 별도로 판정한다.
10. 증거·검수: 스크린샷은 `.gdm/<슬러그>/ui/<이름>-<폭>-<테마>.png`로 저장하고
   `gdm pass --manual --observed`의 증거로, 기계 게이트는 자동 check로 등록한다.
   중량 작업(배포 화면, `--audit`)이면 시각 검수를 받는다 — 검수자는 구현자와
   **다른 모델**의 fresh-context leaf 워커 정확히 1명이다. `MAX_AUDITORS_PER_PASS: 1`,
   `AUDITOR_MAX_AGENT_DEPTH: 0`, `AUDITOR_MAX_CHILD_AGENTS: 0`이며 collaboration
   서브에이전트로 스폰하지 않는다. 프롬프트는
   검수자 프롬프트(`design-auditor.md`) 전문 + 원 요청 + 계약 + 스크린샷·증거 경로.
   `design-auditor.md`는 설치 시 스킬 옆 `gdm-agents/`에 배치된다(소스: 저장소
   `agents/design-auditor.md`). 실행은 반드시 `gdm-agents/run-auditor.sh`를 사용해
   에이전트·사용자 MCP·쓰기 도구를 제거하고 단일 PID 트리에 자원 한도를 적용한다.
   다른 모델 검수자를 실행할 수 없으면 임의로 동일
   모델 검수로 낮추지 말고 `INDEPENDENCE_BLOCKED`를 보고하고 멈춘다 (gdm-full과
   동일 규칙).

## 기계 게이트 — gdm 자동 check 권장 목록

계약 준수를 모델의 성실성에 맡기지 않는다. 자동 check로 등록해 gdm이 판정한다:

- **대비 게이트**: 텍스트와 실제 배경의 토큰 쌍마다 계산한다.
  일반 크기 텍스트는 보조 문구도 4.5:1, 큰 글자(18pt 이상 또는 굵은 14pt 이상)는
  3:1이다. 필요한 UI 식별 요소·상태와 인접 색의 비텍스트 대비는 3:1이며 모든 장식
  구분선에 일괄 적용하지 않는다. 예외와 적용 범위는
  [W3C 텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html),
  [비텍스트 대비](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)를 따른다.
  다음 계산은 단색 sRGB 두 색에 한정된다. 반투명·이미지는 실제 배경을 확인한다:

  ```bash
  node -e 'const a=process.argv[1],b=process.argv[2],t=parseFloat(process.argv[3]||"4.5");
  const L=h=>{h=h.replace("#","");if(h.length===3)h=[...h].map(c=>c+c).join("");
  const[r,g,bl]=[0,2,4].map(i=>parseInt(h.slice(i,i+2),16)/255)
  .map(c=>c<=0.03928?c/12.92:((c+0.055)/1.055)**2.4);
  return 0.2126*r+0.7152*g+0.0722*bl};
  const x=L(a),y=L(b),r=(Math.max(x,y)+0.05)/(Math.min(x,y)+0.05);
  console.log(r.toFixed(2)+":1");process.exit(r>=t?0:1)' "#전경" "#배경" 4.5
  ```

- **하드코딩 차단**: 토큰 파일 밖의 색 리터럴 0건 (예: `! grep -rn -E
  '#[0-9a-fA-F]{3,8}\b' src/ --include='*.tsx' --include='*.css' | grep -v
  <토큰파일>`. 프로젝트에 stylelint가 있으면 declaration-strict-value류 린트로)
- **접근성 바닥선**: `axe <URL> --tags wcag2a,wcag2aa --exit` — exit 1은 진짜
  위반(고쳐라), exit 2는 환경 문제(위반으로 취급 금지). 이미지·그라데이션 위
  텍스트 대비는 이 도구가 판정 못 하고 조용히 통과시킨다 — 채점표 5번이 커버.
- **콘솔 클린**: 렌더 후 브라우저 콘솔에 error 0건 (Playwright MCP
  `browser_console_messages` 또는 playwright 스크립트).

## 채점표 — 렌더에 대조 (정본. design-auditor.md의 사본과 함께 고친다)

각 항목은 스크린샷을 보고 판정한다. 코드 리뷰로 대체할 수 없다.

1. 3초 테스트: 처음 보는 사람이 3초 안에 무엇을 위한 화면인지 말할 수 있는가.
   시선이 처음 닿는 요소가 의도한 그 요소(시그니처)인가.
2. 계층: 크기·무게·색의 단계가 정보의 중요도 순서와 일치하는가. 전부 비슷한
   무게면 실패다.
3. 간격 리듬: 보이는 간격이 전부 토큰 스케일 값인가. 같은 그룹 안 간격이
   그룹 사이 간격보다 좁은가.
4. 정렬: 좌측 정렬 축을 셀 수 있는가(본문 기준 2~3개). 1~2px 어긋난 요소가 없는가.
5. 대비: 일반 크기 텍스트(보조 문구 포함) 4.5:1, 큰 글자 3:1 이상 — 특히 이미지·그라데이션 위 텍스트는
   자동 도구가 못 잡으므로 스크린샷에서 직접 확인한다.
6. 관성 대조: 관성 목록과 대조해 "의도 없이" 들어간 항목이 없는가.
7. 상태·경계: 인터랙티브 요소가 눌러보고 싶게 생겼는가. 긴 텍스트·항목 0개·항목
   아주 많음에서 안 깨지는가.
8. 반응형: 계약의 최소 지원 크기에서 본문 가로 스크롤이 없는가. 터치 타깃이 플랫폼 기준과 계약을 충족하는가.
9. 테마: 다크가 반전이 아니라 설계인가. 단일 테마는 계약에 선언된 선택일 때만.
10. 통합 미감: 전체 구성의 비례·밀도·에셋·글자·색이 선택한 제품 방향을 함께 지지하는가.
    자동 검사 통과만으로 이 항목을 통과시키지 않는다. 부족한 위치와 비교 근거를 명시한다.

**라이브 점검** — 정적 스크린샷으로 판정 불가한 것 (브라우저 조작 가능할 때):

- Tab 순회: 포커스가 눈에 보이고 순서가 논리적인가.
- hover/focus 상태가 실제로 나타나는가 — 상태를 유발한 캡처를 증거에 추가.
- 조작 수단이 없으면 생략하되, 완료 보고에 "라이브 미점검"을 명시한다.

## 렌더 레시피 (폴백 순서대로)

1. Playwright MCP 또는 playwright CLI(node 18+): viewport 지정 스크린샷 +
   콘솔 메시지가 한 세트. `npx playwright screenshot --viewport-size=375,812 <URL> out.png`
2. Chrome headless 폴백: `"<크롬 경로>" --headless=new --hide-scrollbars
   --screenshot=out.png --window-size=1440,900 <URL|file://경로>`.
   IMPORTANT: 데스크톱 크롬은 창 최소폭(~500px) 클램프가 있어 375 같은 모바일
   폭을 `--window-size`로 만들 수 없다 — 좁게 요청해도 넓게 렌더된 것을 잘라
   내놓아, 멀쩡한 코드가 "잘림 결함"으로 오판된다 (실측). 모바일 폭은
   해당 폭의 iframe을 담은 하니스 html을 만들어 넓은 창에서 캡처한다.
3. 앱 화면: 프로젝트 dev 서버 기동 후 위와 동일 — 표준 기동 명령은 `gdm preset` 등록 대상.
4. 어느 것도 불가하면: 프리플라이트에서 선언했듯 렌더 미확인을 명시하고
   사용자 스크린샷을 받아 그 파일로 검증한다.

## 엣지 케이스

- 사용자가 선택한 Claude Design 경로에서 인증·권한·프로젝트 문제가 발생하면 필요한
  조치를 설명한다. 사용자가 직접 진행을 허용하면 `designProvider: coordinator`로 전환한다.
  외부 도구를 선택하지 않은 작업은 외부 도구 가용성과 무관하게 직접 진행한다.
- 화면이 여러 장(사이트·앱 전체)이면: 대표 화면 1장으로 이 루프를 완주해
  프로젝트 층(토큰)을 확정한 뒤, 나머지 화면은 작업 층 spec만 갱신하며
  전개한다. 화면마다 방향 선매를 반복하지 않는다 — 방향은 시스템의 것이고,
  화면의 것은 구조뿐이다.
- 전면 리디자인이면: 변경 전 현재 화면을 같은 폭 조합으로 먼저 캡처해
  `.gdm/<슬러그>/ui/baseline-*.png`로 남긴다 — 비교 증거이자 회귀 방지선.
- 웹폰트를 쓸 수 없는 환경(오프라인·CSP)이면: 시스템 스택 안에서 고른 이유를
  계약에 적는다 — 폴백도 선택이어야 한다.
- 기존 화면의 구체적 결함 수정(잘림·간격·오작동 등)이면 gdm-ui로 전환한다.
  기존 컴포넌트라도 새로운 시각 방향을 정해야 하는 요청은 이 스킬에서 범위를 좁혀 진행한다.

## 출력 형식

기본 완료 보고는 적용한 방향과 변경 → 계약·스크린샷 경로 → 검증 결과와 미검증 범위다.
Claude Design을 명시적으로 요청받은 handoff turn에만 프롬프트, 실행 위치,
회신받을 프로젝트 이름/ID와 완료 여부를 전달한다.

## 예시

Bad — 브리프를 받자마자 코드부터 (거부되는 방식):

```
대시보드를 만들어달라고 하셨으니 바로 App.tsx를 만들겠습니다. 보라 그라데이션
헤더에 카드 그리드를 깔고... 완료했습니다.
```

방향도 계약도 렌더 확인도 없다. 이렇게 만든 화면이 "AI가 만든 것 같다"는 말을
듣는 바로 그 화면이고, 완료 주장에 스크린샷이 없으므로 검증 불가다.

Good — 기본 역할 분담:

```text
사용자: 일정 관리 대시보드가 너무 복잡하고 안 예뻐요.

1. 총괄이 기존 화면·토큰·실제 일정 데이터를 읽고 대표 화면과 개선 범위를 정한다.
2. UX 담당은 일정 확인→수정→완료 흐름, 레이아웃 담당은 오늘·예정·완료의 정보 순서를 검토한다.
3. 같은 구조를 타이포 담당은 한글 제목·날짜·보조 문구, 색 담당은 강조·상태·표면 관점에서 검토한다.
4. 총괄이 의견을 하나의 계약으로 통합하고, 지정된 구현 담당이 대표 화면을 수정한다.
5. 같은 데이터의 좁은·넓은 화면을 다시 보고 역할별 결함을 고친 뒤 나머지 화면에 확장한다.
6. 완료 보고에 변경 이유, 참여 역할, 실제 화면 증거와 미확인 조작을 적는다.
```

Good — 사용자가 선택한 외부 디자인 연동:

<example>
사용자: 러닝 기록 앱 대시보드 만들어줘. Claude Design을 사용해줘. $gdm-design

어시스턴트:
1. 로컬 데이터·상태·토큰을 확인한 뒤 Claude Design용 프롬프트를 코드 블록으로 전달:
   "러닝 기록 대시보드다. 야간 트랙 전광판과 종이 기록장이라는 서로 다른 방향
   2안을 먼저 비교하고, 오늘 기록·주간 그래프·목표와 비어있음/로딩/에러 상태를
   375/768/1440 기준으로 설계하라..."
2. "claude.ai/design에서 실행한 뒤 프로젝트 이름/ID와 생성 완료 여부를 알려주세요."
3. (사용자: run-dashboard 생성 완료) `/design-sync`로 지정 프로젝트를
   list/get하여 결과를 pull. 선택된 "트랙의 밤"을 tokens.css와 spec으로 계약화.
4. 구현 → 375/768/1440 렌더 → 채점: 3번 미달(카드 내부 20px — 스케일 밖),
   1번 미달(오늘 기록보다 주간 그래프가 먼저 읽힘) → 수정 → 재렌더 통과.
   기계 게이트: 하드코딩 0건, axe 위반 0건, 콘솔 에러 0건 (자동 check 통과)
5. "완료: '트랙의 밤'. 계약 tokens.css + .gdm/run-dash/design/spec.md,
   스크린샷 3장, 채점 10항목 통과(2항목 1차 미달 후 개선), Tab 순회 확인.
   axe는 자동 검출 위반 0건까지만 의미합니다 — 대비는 채점표에서 직접 봤습니다."
</example>

<commentary>
이 예시는 사용자가 외부 도구를 명시적으로 선택한 경우다. 기본 직접 디자인에서는
외부 프롬프트 전달·사용자 생성 대기·pull이 필요 없다.
선택적 경로에서 브라우저를 대신 조작하지 않고 프롬프트를 전달해 Claude Design의 실제 생성
경계를 지켰고, 사용자 확인 뒤 결과를 pull했다. 토큰이 값의 출처가 됐고, 첫 렌더의
결함을 채점표가 잡았으며, 계약 준수는 기계 게이트가 판정했다.
</commentary>
