# Pi 실제 Astra 협업 개선과 비교 결과

Terra high를 메인, Luna medium을 선택적 조사, Astra medium을 설계·검토로 사용하는 설정을 적용했다. 동작 변경은 완료 전에 reviewer를 호출하고, 구조·모듈 간 상태·권한·트랜잭션·동시성 변경은 구현 전 design도 호출한다. 문서·서식은 제외한다. 거부·실패·빈 응답은 역할 완료가 아니며, 지적을 반영하거나 기각 이유를 남기고 검토 이후 동작이 달라지면 다시 검토한다. 이는 실행 지침이며 모든 작업의 자문 품질을 강제하는 런타임 판정기는 아니다. 새 `gdm-pi` 세션부터 적용된다.

다중 모듈 합성 과제 4종에서 세 구성으로 각각 한 번씩, 총 12회 실행했다. 모든 메인은 Terra high이고 전문 역할은 medium이다. 협업 구성은 구현 전 설계와 최종 소스 검토가 실제로 성공했는지 확인했다. 숨긴 요구사항 36개와 원래 테스트를 동일하게 채점했다.

| 구성 | 기능 요구사항 | 실제 설계 / 검토 성공 | 완료 시간 중앙값 |
|---|---:|---:|---:|
| Terra 단독 | 36/36 | 0 / 0 | 175.3초 |
| Terra 설계·검토 | 36/36 | 4 / 6 | 281.6초 |
| Astra 설계·검토 | 36/36 | 4 / 4 | 267.2초 |

**이번 표본에서는 Astra의 최종 품질 우위를 확인하지 못했다.** 같은 과제를 짝지은 비율의 중앙값에서 Astra 협업은 단독보다 시간 62.7%, API 추정 비용 96.8%가 늘었다. Terra 협업과 비교하면 시간은 거의 같고 API 추정 비용은 35.1% 높았다. 목록 가격으로 계산된 Pi 보고값이며 구독 크레딧이나 실제 청구액이 아니다. 따라서 Terra를 메인으로 유지하고 Astra를 설계·검토 역할에 한정한다. Astra 전문 역할의 우월성이 입증됐다는 의미로 이 운영 선택을 설명하지 않는다.

검토 직전과 최종 소스의 사전 등록 검사 점수는 같았다. 별도로 Terra 예약 검토자의 입력 타입 지적을 관찰한 뒤 세 구성에 같은 탐색 검사를 적용했다. 해당 Terra 협업 실행은 검토 전 실패, 수정 후 통과했고 Terra 단독 최종 코드 및 Astra 검토 전·최종 코드도 통과했다. 검토가 그 실행의 입력 방어를 보완한 사례는 확인됐지만 최종 구성 간 차이는 아니다. 같은 검토자가 요구한 버전 오버플로 방어는 과제에서 제외한 입력 범위이므로 결함 제거로 세지 않았다. 탐색 검사로 원래 점수를 변경하지 않았다.

실제 gdm 완료는 12/12였다. 콜론까지 요구한 별도 완료 마커의 불일치 7건 때문에 사전 등록 전체 `success`는 5/12이며 이 원판정도 보존한다. 기능 검사, gdm 완료, 출력 형식을 구분한다. 네 과제와 한 번의 반복으로 실서비스 품질이나 안정적인 모델 우열을 일반화할 수 없다.

처음의 문제도 수정했다. scout의 medium/high를 거부하던 검증기를 공개 스키마와 일치시켰고, 위임 오류를 Pi 바깥 tool event에도 전달했다. 요청·거부·시작·정상 응답을 분리하고 빈 응답은 실패로 처리한다. 과거 64회 실험에는 scout 시도 1회가 있었지만 거부되어 실제 자식은 0회였다는 정정도 기존 분석기에 반영했다.

비교 입력은 0.12.0으로 동결했다. 후속 0.12.1은 실행 파일을 시작하지 못한 경우를 launched로 세던 계측 오류만 고쳤다. 모델 배분·지침·채점 조건은 동일하며, 정확한 세 파일 차이를 `telemetry-patch.diff`와 검증 기록에 남긴다. 설치본에서 고의로 잘못된 요청 1회를 보낸 뒤 Luna 조사와 Astra 설계·검토가 실제 성공하는 별도 프로브도 확인했다. 이 프로브는 품질 비교에 합산하지 않는다. 기존 설정과 설치본은 버전별로 백업했다.
