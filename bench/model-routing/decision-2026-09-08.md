# Pi / gdm 모델 운영 결정 — 2026-09-08

Terra high를 일상 구현과 작업 진행의 기본으로, Luna medium을 범위가 명확한 조사 작업자로, Astra medium을 설계·중요 코드 검토 담당으로 사용한다. 어려운 설계·교차 파일 결함은 Astra high로 올린다. Astra의 직접 구현도 복잡한 작업에서는 허용한다.

이는 공개 자료와 현재 Pi 구조를 바탕으로 정한 초기 운영안이다. Pi에서 이 조합의 비용·시간·성공률 우위를 직접 측정한 결과는 아니다. 이번 조사에서는 설정과 실행 코드를 바꾸지 않았다.

## 확인한 주장과 실제 출처

### 티보: Astra 메인 사용 금지보다 추론 강도 조정

티보는 Thibault Sottiaux(@thsottiaux)로 확인했다. [본인 프로필](https://www.linkedin.com/in/thibault-sottiaux-27195366)이 해당 X 계정을 연결한다.

- **2026-09-06 발언:** Astra low가 Sol high보다 좋은 성능을 내므로, Sol high에 만족했다면 Astra에서는 low 또는 medium부터 사용하라는 권고다. [X 원문 링크](https://x.com/thsottiaux/status/2096688770523467947)
- X 본문에는 직접 접근하지 못했다. [OpenAI 개발자 커뮤니티 게시물](https://community.openai.com/t/set-astra-low-medium-as-a-replacement-for-5-6-sol-high/1395421)에 보존된 인용 전문과 원문 연결을 확인했다. 커뮤니티 작성자는 Astra low를 조율 담당으로, 추가 절약에는 Luna/Terra를 제안한다. 이 해석은 일반 회원의 글이며 OpenAI 공식 정책이 아니다. 게시일 메타데이터가 도구별로 달라 커뮤니티 글의 정확한 게시일은 확정하지 않았다.
- **2026-08-15 발언:** Sol이 효율적인 Luna 작업자들을 관리하게 하자는 내용이다. [X 원문 링크](https://x.com/thsottiaux/status/2088725163923984638). 직접 X 본문은 읽지 못했고, [8월 16일 재게시의 임베드](https://m.dcinside.com/board/chatgpt/123576)와 [8월 17일 TestingCatalog 기사](https://testingcatalog.net/openais-codex-update-lets-sol-hand-off-grunt-work-to-luna/)를 확인했다. 설계·최종 검토 Sol / 구현 Luna라는 상세 배분은 기사의 해설이다. Astra 출시 전 발언이다.

따라서 “티보가 Astra를 메인으로 쓰지 말고 설계·검토에만 쓰라고 했다”는 정확한 주장은 이번 검색에서 확인하지 못했다. 두 관련 발언을 합쳐서 그런 공식 권고로 인용하지 않는다.

### CodeRabbit: Astra의 중요한 검토 역할을 뒷받침

[CodeRabbit, 2026-09-04](https://www.coderabbit.ai/blog/gpt-6-astra-code-review-evaluation)은 자체 평가에서 Astra가 Sol보다 전체 정답 버그를 약 4% 더 찾았고, 여러 파일의 정보를 연결해야 하는 어려운 부분집합에서는 약 20% 더 찾았다고 보고했다. 두 수치는 상대 개선율이며 퍼센트포인트가 아니다.

이 결과는 Astra에 복잡한 코드 검토를 맡기는 판단을 지지한다. Terra/Luna와의 직접 품질 비교, Pi에서의 성능, 특정 reasoning 설정의 우위를 입증하지는 않는다. 업체의 초기 평가이고, 팀의 실제 결함 감소율로 그대로 환산할 수 없다.

### 반대 근거: Astra를 구현에서 배제하면 안 되는 이유

[Artificial Analysis, 2026-09-03](https://artificialanalysis.ai/articles/benchmarking-gpt-6-astra)은 Codex에서 Astra가 Sol max보다 토큰을 약 70% 적게 사용하며, max끼리 비교하면 비슷한 작업당 비용으로 Coding Agent Index가 2점 높았다고 보고했다. 다른 일반 지능 평가에서는 비용 양상이 달랐다. 모델의 토큰 단가만으로 완료 비용을 판단할 수 없다는 반례다. Pi 또는 Terra/Luna와의 직접 비교는 아니다.

[Kilo, Ari Messer, 2026-09-04](https://blog.kilo.ai/p/gpt-6-astra-what-we-learned-previewing)는 실제 기능 구현·리팩터링·리뷰 등에 Astra를 사용했고 high 설정으로 자체 벤치마크 최고 결과를 얻었다고 보고했다. 긴 구현 작업에 적극 활용하는 경험담인 동시에, 작은 수정의 과도한 확장과 지나친 조사를 비용 증가 요인으로 지목했다. 제품 업체의 경험담이며 독립적인 Pi 비교 실험은 아니다.

## Terra를 메인으로 선택한 이유

[공식 모델 선택 지침](https://developers.openai.com/api/docs/guides/model-selection)은 필요한 정확도를 먼저 정하고 이를 유지하는 더 빠르고 저렴한 모델을 평가하라고 안내한다. 가장 비싼 모델을 항상 쓰거나 무조건 배제하라는 규칙이 아니다.

[Terra 모델 설명](https://developers.openai.com/api/docs/models/gpt-5.6-terra)은 능력과 비용의 균형을, [Luna 모델 설명](https://developers.openai.com/api/docs/models/gpt-5.6-luna)은 비용에 민감한 대량 작업을 중심으로 둔다. [Codex 가격 안내](https://developers.openai.com/codex/pricing)도 Terra를 일상 기본 모델, Luna를 가벼운·대량 작업 모델로 설명한다.

gdm 메인은 요구 해석, 여러 파일의 수정, 도구 실행, 검증 결과 판단까지 맡는다. 이 책임에는 Terra를 기본으로 두고 Luna는 분리 가능한 작은 작업부터 맡기는 구성이 적절하다고 판단했다. 이것은 Luna가 복잡한 코딩을 못 한다는 주장이 아니다. [GPT-5.6 공식 발표](https://openai.com/index/gpt-5-6/)도 Luna의 상당한 코딩 성능을 보고한다. 다만 공개 벤치마크만으로 이 저장소의 장기 작업 진행 능력까지 같다고 가정하지 않는다.

## 결정한 역할과 추론 강도

`low`, `medium`, `high`는 답하기 전에 추론에 쓰는 노력의 설정이다. 서로 다른 모델에서 같은 이름이 같은 비용이나 성능을 뜻하지는 않는다.

| 역할 | 기본 모델·강도 | 맡길 작업과 승격 기준 |
|---|---|---|
| 일상 메인 | **Terra high** | 기능 구현, 버그 수정, 테스트 실행, 작업 진행·통합. 명백히 단순한 작업은 medium으로 시작 가능 |
| 조사 작업자 | **Luna medium** | 정해진 디렉터리의 파일 찾기, 호출 지점 조사, 관련 테스트·문서 위치 수집. 구조 해석의 불확실성이 커지면 Terra로 승격 |
| 설계 자문 | **Astra medium** | 대안 선택, 여러 모듈의 책임·계약, 변경 범위와 검증 전략. 단순 수정에는 별도 설계 호출을 생략 |
| 중요한 코드 검토 | **Astra medium** | 구현자와 별도 문맥에서 diff·관련 소스·검증 결과를 확인. 인증·권한·데이터 무결성·교차 파일 불변식은 high |
| 복잡한 직접 구현 | **Astra medium → high** | Terra가 새 증거 없이 같은 수정 가설을 반복하거나, 설계와 실행을 분리하면 정보 손실이 큰 작업. 처음부터 복잡성이 드러나면 바로 선택 |

강도 설정은 운영 가설이다. 특히 CodeRabbit의 상대 개선율이 Astra medium에서 그대로 나온다고 주장하지 않는다. [공식 reasoning 안내](https://developers.openai.com/api/docs/guides/reasoning)는 작업에 맞는 강도와 추가 노력의 실익 평가를 권한다.

항상 max/xhigh로 시작하지 않는다. Astra의 역할 제한도 금지 규칙으로 만들지 않는다. 판단을 돕지 않는 모델 교대, 작은 변경마다 설계자·검수자를 의무 호출하는 단계도 추가하지 않는다. 승격은 작업 중단이나 사용자 재승인을 뜻하지 않는다.

Luna가 단순 작업에서 실패했다면 누락된 입력·범위 문제와 모델 능력 문제를 먼저 구분한다. 새로운 근거 없이 재시도만 반복하지 않고, 필요한 소스와 실패 기록을 상위 모델에 넘긴다. 구현 코드는 메인이 통합하고 실제 테스트로 확인한다.

## 비용을 해석하는 방법

일반 API의 100만 토큰당 표준 가격은 아래와 같다. 272K 이하 입력, 캐시 미사용 기준이다.

| 모델 | 입력 | 출력 | 입력 100K + 출력 10K를 사용한 계산 예 |
|---|---:|---:|---:|
| [Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna) | $0.20 | $1.20 | $0.032 |
| [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) | $2.00 | $12.00 | $0.320 |
| [Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) | $10.00 | $50.00 | $1.500 |

이는 토큰량을 같게 놓은 산술 예이며 실측 작업 비용이 아니다. 실제로는 추론·캐시·실패 후 수정·검토까지 포함한 완료 비용이 중요하다.

현재 Pi provider는 `openai-codex`다. 따라서 API 달러 가격 비율을 사용자의 구독 한도 절약률로 바꾸지 않는다. [Codex 가격 안내](https://developers.openai.com/codex/pricing)는 구독 한도가 모델·문맥·추론·도구·캐싱에 따라 달라진다고 설명한다. 확인한 페이지의 표에는 Astra가 없고 이전 가격 조정과의 정합성도 확정하지 못해, Astra의 구독 크레딧 배수는 이 보고서에서 제시하지 않는다.

## 다음 A/B에서 판별할 것

이번에는 공개 벤치마크를 조사했으며 신규 Pi 모델 A/B를 실행하지 않았다. 앞서 수행한 `bench/astra-ablation/analysis-2026-09-08.md`는 같은 Astra에서 지침을 비교한 실험이다. 그 결과는 모델 순위의 근거가 아니다.

1. **메인 비교:** 동일한 개선 후 지침·Pi 버전·도구·문맥·시간 상한에서 `Sol xhigh`, `Terra high`, `Luna medium`, `Astra low`를 비교한다. 기본 비교에는 Astra low를 포함해 과도한 추론 설정으로 Astra를 불리하게 만들지 않는다. 난도별 강도 상향 비교는 별도 기록한다.
2. **조합 비교:** Terra 단독과 Terra + Luna 조사 + 필요한 Astra 설계·검토를 비교한다. 메인 변경 효과와 위임 효과를 한 번에 섞지 않는다. 검토로 발견한 결함을 실제 수정하는 시간도 포함한다.
3. **과제:** 단순 수정, 여러 파일의 기능 변경, 인증·DB 계약 오류, 간헐적 실패 진단을 포함한다. 모델에 보이지 않는 정답 테스트와 결함 기준을 실행 전에 정한다.
4. **판정:** 성공률·중대한 누락을 먼저 보고, 성공한 작업당 전체 시간·사용량·재작업·모델 교대 비용을 비교한다. 모델 채점은 익명·셔플하고 동일 기준을 쓴다. 실패·timeout·usage 누락도 모두 남긴다.
5. **규모와 한계:** 우선 난도별 과제를 포함한 최소 8개 과제 × 4개 메인 × 2회 교차 반복을 파일럿으로 삼을 수 있다. 작은 차이는 확정 순위로 발표하지 않는다. 이 실행은 현재 보고서에 포함된 완료 작업이 아니다.

현재 결정의 신뢰도는 **역할 분담 방향: 중간 이상**, **정확한 추론 강도: 중간**, **Pi에서의 절약률·속도 개선: 아직 미측정**이다.
