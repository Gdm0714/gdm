# Computer Use: 모델 후보 생성 + Jev 선택 실측

Rust 실행기, 공식 Claude CLI의 같은 모델, 실제 TypeSafe API와 전용 macOS VM을 사용했다.
모델은 화면을 보고 2~4개의 구체적인 행동 후보를 만든다. 기준군은 같은 호출에서
하나를 선택하고, 실험군은 후보 선택만 Jev에 맡긴다. Jev 뒤에 추가 모델 호출이나
숨겨진 재시도는 없다. 모델이 반환한 모델명과 사용량도 결과 JSON에 기록한다.

실험 과제는 TextEdit에서 선택된 문자열을 정해진 문자열로 교체하는 단일 행동이다.
실제 저장된 파일의 내용을 별도로 확인한다. 두 군의 실행 순서를 번갈아 배치하며
후보 생성, Jev 선택, GUI 실행, 파일 검증 시간과 실패를 모두 남긴다.

별도로 수행했다.

`verified-08.json`, 2026-09-21, 같은 `sonnet` 요청 모델
(CLI 보고값 `claude-sonnet-5`), Jev `jev-1.13.0`:

| 방식 | 저장 검증 성공 | 전체 지연 중앙값 | 관측 p95 |
|---|---:|---:|---:|
| 기존 모델이 후보 생성과 선택 | 3/3 | 9,155ms | 13,263ms |
| 기존 모델이 후보 생성, Jev가 선택 | 3/3 | 9,852ms | 11,498ms |

Jev 선택은 **539~670ms**였다. 전체 지연 중앙값은 Jev 군이 **약 7.6% 느렸다**.
p95는 표본이 3개라 사실상 관측 최댓값이며 통계적인 꼬리 지연 추정이 아니다.
이 조건에서는 가속 효과를 확인하지 못했다. 키 설정과 실제 후보 선택·실행 경로가
작동하는 것은 확인했으므로 기능은 선택 가능한 실험 경로로 유지한다.

최종 원본은 GDM이 직접 실행·해시한 `c7` 증거 안에도 포함되어 있다.
`verified-08.json`은 그 원본 JSON을 바이트 변경 없이 복사한 파일이다.

## 재현과 해석

```sh
cargo build --locked
python3 script/qa/rust-jev-live.py --env-file /absolute/path/to/.env --repeats 3
```

이 검사는 실제 과금 가능한 모델 호출과 전용 VM을 사용하므로 기본 단위 테스트에
포함하지 않는다. API 키는 읽기만 하며 결과에 포함하지 않는다.
검사 성공 조건은 측정과 실제 동작 확인이다. 속도 개선은 성공 조건이 아니다.

v2 `end_to_end_ms`는 후보 생성부터 입력 후 화면 획득까지이며 파일 검증을 제외한다.
`attempt_wall_ms`는 검증까지 포함한다. VM 부팅과 문서 초기화는 둘 다 제외한다.
각 후보 생성마다 새 CLI를 실행하므로 지속 세션을 사용하는 gid와 같은 지연은 아니다.
실패 시도도 분모에 포함하며 두 군의 양의 성공률이 같을 때만 속도 비율을 계산한다.

단순한 한 행동 과제, 작은 표본, 네트워크와 모델 응답 편차가 있는 실험이다.
복잡한 작업의 성공률이나 일반적인 가속 효과는 입증하지 않는다. 매번 후보를 새로
만드는 구조에는 Jev 왕복 시간이 추가된다. 비싼 별도 판단 단계를 대체하거나 후보를
재사용할 때 이득이 있는지는 별도의 실험이 필요하다. Jev 경로는 선택형 실험 기능이다.

## 후속 실험: 후보를 재사용하는 여러 단계 작업

`benchmark-reuse`는 기존 모델이 생성한 후보를 재사용하며 Jev가 매 단계 선택한다.
같은 전용 VM에서 이름, 도시, 인원, 확인을 입력하는 Rust 폼을 사용한다. 모델에는
합성 화면과 폼의 실제 상태만 보낸다. TextEdit의 접근성 관측은 기존 권한으로 응답하지
않았으므로, 권한을 추가하지 않고 상태를 직접 제공하는 실험 폼으로 대체했다.

비교군은 매 단계 모델 호출, 한 번의 모델 호출로 전체 순서 계획, 한 번의 후보 생성과
단계별 Jev 선택이다. 세 군 모두 같은 입력 제한과 실행 직전 검사, 실행 결과 확인을
거친다. 후보 문자열은 합성 목표의 네 값으로 한정하며 선택기는 새 행동을 만들 수 없다.
화면 불일치나 기권은 입력을 중단하고, Jev 군은 같은 폼에서 후보를 한 번만 재생성할
수 있다. 재생성 시간과 실패를 결과에 포함한다.

모델 호출을 줄인 이득을 Jev 고유의 이득으로 오해하지 않도록 **모델의 일괄 계획**을
비교군으로 유지한다. 정해진 순서의 단순 폼은 일괄 계획에도 유리한 조건이다.
각 모델 호출은 새 공식 CLI 프로세스이며, 이 시작 비용과 도구의 상태 조회 비용도
전체 수행 시간에 포함된다. 임의의 웹사이트나 데스크톱 앱을 대표하는 벤치마크는 아니다.

### 준비 과정에서 발견한 문제

| 파일 | 관측 및 조치 |
|---|---|
| `reuse-pilot-01.json` | 단계별 모델의 계획 ID 또는 길이 검증 실패. 일괄 계획과 Jev 재사용은 각각 네 단계 수행 성공. |
| `reuse-pilot-02.json` | 모델이 ID 대신 설명문을 반환한 것을 기록으로 확인. 한 행동 선택에는 `selected_id`를 쓰도록 계약 명확화. |
| `reuse-pilot-03.json` | 화면 불일치와 모델 입력의 줄바꿈 누락을 거부. 목표의 정확한 입력 문자열을 JSON 스키마에도 명시. |
| `reuse-pilot-04.json` | 진단 이미지의 변화가 Terminal 우측 상단 14×14 영역에 국한됨을 확인. 새 프로세스에만 활동 표시 옵션을 지정하고 시작 안정화 시간을 준비 단계에 추가. |
| `reuse-preflight-05.json` | 모델이 후보 ID에 입력 문자열을 넣어 선택 ID와 불일치. 식별자 계약 결함을 확인한 뒤 해당 실행만 취소하고 기록 보존. Rust가 ID를 부여하고 모델은 배열 번호를 선택하도록 수정. |
| `reuse-stale-06.json` | 초기화 뒤 첫 모델 입력의 화면 해시가 직전 작업의 마지막 화면 해시와 같은 사례를 확인. 상태와 화면이 불일치한 측정을 취소하고 기록 보존. 성능이나 모델 정확도의 근거로 사용하지 않음. |
| `reuse-sync-check.json` | 모델 호출 없이 입력 경로로 두 번 초기화하고 여덟 단계의 실제 상태와 화면 일치를 확인. |

전체 픽셀 해시 검사와 실행 직전 상태 확인은 유지했다. 진단 이미지는 `/tmp`에만
저장했다. 초기 실패 JSON도 보존하며, 서로 다른 구현으로 얻은 파일을 최종 수치에 섞지 않는다.

최종 실험 폼은 별도 화면 버퍼를 사용하고 단계마다 다른 배경색 표식을 출력한다.
초기화도 전용 폼의 입력 경로로 실행한다.
입력 단계와 맞는 표식이 보이고 전체 화면이 연속 두 번 같아야 해당 화면을 모델에
전달하거나 실행 결과로 인정한다. 표식 색은 렌더링 편차를 고려해 채널별 6/255 범위로
확인하며, 실행 직전 전체 화면 SHA-256의 동일성 검사는 정확히 유지한다. 이 표식은
실험 폼의 단계 동기화 수단이며 범용 앱의 상태 인식이나 권한 판정을 대신하지 않는다.
동기화 비용은 세 군 모두의 작업 시간에 포함한다.

### 동기화를 검증한 5회 비교 결과

`results/reuse-final.json`, 2026-09-21. 같은 공식 Claude CLI의 `sonnet`
(보고 모델 `claude-sonnet-5`)과 Jev `jev-1.13.0`, Rust debug 빌드로 측정했다.

| 방식 | 최종 입력 검증 성공 | 모델 호출/시도 | 전체 시도 지연 중앙값 | 성공한 작업의 지연 중앙값 |
|---|---:|---:|---:|---:|
| 매 단계 모델 생성·선택 | 5/5 | 4 | 82,748ms | 82,748ms |
| 모델이 후보와 전체 순서 계획 | 4/5 | 1 | 63,232ms | 63,075ms |
| 모델 후보 재사용 + Jev 선택 | 4/5 | 1 | 69,882ms | 70,666.5ms |

후보 재사용으로 기존 모델 호출은 **4회에서 1회로 감소**했다. Jev는 총 19회 호출됐고,
선택 호출 시간의 중앙값은 **538ms**, 범위는 **476~2,014ms**였다. 성공한 네 작업에서는
각각 후보 한 묶음으로 네 번 선택했다. 이 측정에서 후보 재생성은 발생하지 않았다.

일괄 계획 군과 Jev 군에서 각각 한 번 `reuse_visual_sync`로 중단됐다. 현재 단계의 화면이
안정되었음을 제한 시간 안에 확인하지 못한 사례이며, 이 실패들을 제거하거나 성공으로
바꾸지 않았다. `steps`에는 화면과 상태까지 검증한 입력만 기록되므로, 중단된 시도의
마지막 입력은 실제 전송되었어도 검증 완료 단계에 포함되지 않을 수 있다.

**호출 감소는 확인했지만, 성공률이 다른 세 군의 속도 우위는 확정하지 않는다.** 결과 JSON의
가속 비율도 `null`로 유지한다. 성공한 작업에서 관측한 중앙값은 일괄 계획이 가장 짧았다.
이 단순 폼에서는 실행 순서를 처음부터 정할 수 있으므로, 이득 전체를 Jev 덕분이라고
해석할 수 없다. 또한 화면 관측과 동기화 비용이 크고 표본이 작다. 일반 앱이나 지속
세션을 사용하는 gid의 실제 지연을 입증한 결과가 아니다.

따라서 이 구현은 후보 재사용과 중단 조건을 검증하는 선택형 실험 경로로 유지한다.
현재 과제의 다음 개선 대상은 화면 관측·동기화 안정성과 관측 비용이다.

### 재현

```sh
cargo build --locked
python3 script/qa/rust-jev-reuse.py \
  --env-file /absolute/path/to/.env --repeats 5 \
  --output /tmp/jev-reuse-results.json

# 추가 모델 호출 없이 저장된 결과와 현재 실험 코드의 일치를 검증
python3 script/qa/rust-jev-reuse.py --verify /tmp/jev-reuse-results.json
```

출력에는 각 단계의 모델 후보와 선택, 실제 입력, 검증된 폼 상태, 모델 사용량,
Jev 분포와 사용량, 호출 횟수, 실패와 시간, 실험 소스의 SHA-256이 들어간다.
초기화와 최종 별도 파일 검증은 작업 지연에서 제외한다. 세 군의 모든 시도가 성공한
경우에만 가속 비율을 제공한다. 기본 MCP 또는 gid 실행 경로로 자동 적용하지 않는다.
