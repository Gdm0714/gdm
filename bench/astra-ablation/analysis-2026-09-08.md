# Astra 전환을 위한 gdm 지침 분석

우선 개선할 것은 **자연어 계약의 과도한 거부와 CLI 도움말**, 그리고 **작업에 맞춘 검증 절차 선택**이다. 지침을 길이 기준으로 일괄 분리하는 변경은 속도 이득이 확인되지 않아 적용을 보류하는 편이 낫다. 아래에서 실제 실행 결과, 기계적으로 재현한 문제, 후속 실험 가설을 구분한다.

## 실측 결론

- **18회 실행 중 15회가 hidden/visible·원래 테스트 보존·실제 done·evidence hash 검증을 모두 통과했다.** 3회는 환경 중단으로 완료하지 못했다.
- 비용 측정에 유효한 실행은 **14회**다. 중단 3회와 모델 목록 갱신 timeout 경고가 있던 완료 1회를 보수적으로 제외했다. 제외 목록은 아래에 공개한다.
- 세 arm 모두 유효한 같은 과제·반복은 **3묶음, 9회 실행**이다: t1/trial1, t1/trial2, t2/trial2. 독립 과제 종류는 2개다. 파서(t3)는 같은 조건의 완전한 비교가 성립하지 않았다.
- 이 9회는 hidden 57개와 원래 visible 45개를 모두 통과했다. 검사의 개수를 독립 표본 수로 계산하지 않는다.

다음은 위 3묶음만 사용하는 run별 중앙값이다. 전체 개별값과 변화율은 [실행 결과표](results-2026-09-08.md)에 있다.

**C는 A보다 같은 과제의 세 비교에서 모두 빨랐다: 6.6%, 4.4%, 10.6% 감소, 짝별 감소율 중앙값 6.6%.** B 대비로도 모두 빨랐고 짝별 감소율 중앙값은 17.3%다. 이는 go의 검증 게이트를 유지하면서 절차를 작업에 맞추는 방향을 추가 검증할 근거다.

**B의 일괄 분리는 속도 개선 근거가 되지 않았다.** 본문 bytes는 28,492 → 10,140으로 64.4% 줄었지만, A 대비 시간은 세 쌍 중 두 쌍에서 증가했다(짝별 변화율 중앙값 +15.6%). 일반 실행 예시까지 함께 분리했으므로 protocol만의 효과는 알 수 없다.

**fresh input은 과제별로 반대 방향이었다.** C는 A 대비 버그 과제에서 34.4%, 55.2% 줄었으나 기능 추가의 정상 비교에서는 43.4% 늘었다. 기능 추가의 첫 반복에서도 C는 B보다 51.3% 더 사용했다. 시간과 토큰이 함께 줄었다고 일반화하거나 실제 요금 절감으로 환산하지 않는다. 표의 중앙값 비율과 짝별 변화율의 중앙값은 다른 통계다.

별도 관찰로 **privacy_rejected가 포함된 명령 결과 23회**, **도움말 관련 non-zero 명령 10회**가 기록됐다. 횟수는 독립 장애 수나 해당 오류만의 시간 비용을 뜻하지 않는다. [자연어 재현 probe](contract-probe.ts)는 일반 문장 3개가 거부되는 것을 확인했고, 합성 credential 대조군의 차단은 유지됐다. 이 문제는 C arm에서 수정하지 않았으며, 수정 후의 순수 시간 이득은 아직 측정하지 않았다.

중단 실행을 성공한 재실행으로 교체하지 않았다. idle sleep 억제는 첫 장애 뒤 runner PID에만 연결했고, 마지막 종료 시 해당 프로세스도 자동 종료됐다. 강제 중단/시간 불일치를 없앴다고 주장하지 않는다.

최초 runner가 완료 파일명을 잘못 조회한 오류는 **모든 arm을 동일하게** 실제 `checks.json`·done 명령·evidence hash로 재채점하여 보정했다. 원시 결과를 덮어쓰지 않았다. 완료 판정은 `assessed.json`이 정본이며 최초 raw `success` 필드는 사용하지 않는다. 이 보정은 프롬프트, 모델 실행, hidden 결과, 시간, usage를 바꾸지 않는다.

**결론의 강도는 탐색적이다.** 정상 비교가 두 과제 종류의 세 묶음뿐이고 이전 모델 대조군도 없다. Astra 고유 효과, 대규모 저장소 품질 비열등성, 각 조항의 단독 효과를 입증한 실험은 아니다. 제품/설치 지침에는 후보를 적용하지 않았고, 벤치 도구와 분석 자료만 추가했다.

## 측정 조건

- 기준 저장소: `5a9d331`, Codex CLI `0.153.4`, 현재 설치 gdm CLI **0.9.1**. 저장소의 `cli/package.json`은 **0.10.0**이다. 스킬은 현재 소스와 같고 실행 파일은 이전 버전인 상태를 그대로 고정했다.
- 모델 요청: `gpt-6-astra`, reasoning `xhigh`. 현재 사용자 설정과 같은 추론 강도다.
- 과제: 한도 0·전동 집계 버그 수정(t1), 백분위·CSV 기능 추가(t2), 기존 파서 호환성을 보존하는 안전 파서 추가(t3).
- 3 arms × 3 tasks × 2 trials = 18회. task별 첫 arm을 회전하고 두 번째 trial에서 순서를 뒤집는다.
- 실행마다 새 fixture·Git 기준선·ephemeral session. 개인 config·rules·프로젝트 지침 자동 주입과 외부 도구를 제외하고 동일한 조건으로 실행한다.
- 숨긴 테스트는 실행이 끝난 뒤 복사하여 기계 채점한다. 원래 visible test의 bytes 보존, 실제 `gdm done`, evidence hash도 확인한다.
- 시간, total/cached/fresh input, output, 명령 수, check 수를 기록한다. fresh input은 `input_tokens - cached_input_tokens`이며 실제 청구액은 아니다.
- 분리 실험을 위해 외부 설계·다중 에이전트·브라우저 호출을 모든 arm에서 제외했다. 따라서 그 기능의 가치나 모델 교체 효과는 이번 E2E의 결론에 포함하지 않는다.

`current`는 소스 template가 아니라 **현재 설치된 Codex용 렌더 결과**다. 13개 스킬을 현재 소스로 다시 렌더한 결과가 모두 설치본과 byte 단위로 일치했다. 기존 `bench/run.sh`는 모델과 reasoning을 지정하지 않고 로그·디렉터리를 arm 이름으로 재사용하므로 이번 측정에는 사용하지 않았다.

`ondemand`는 adapter·Work protocol·native delegation·웹/도메인 설명과 일반 실행 예시를 본문에서 분리했다. `calibrated`는 여기에 check 수 유연화, 복잡성 위험에 따른 static 증명, 반복 실패/adopted habit에 따른 회고, 적절한 검증 후 종료 기준을 적용했다. 모든 arm에서 실제 CLI evidence·red→green·경로 범위·done은 유지했다.

## 유지할 경계

- 검증 명령을 CLI가 실제 실행하고 exit code·출력 bytes·hash를 보존하는 구조.
- 기존 결함에 대한 red→green, 숨긴 수용 조건과 원래 동작의 보존.
- 기준을 몰래 완화하지 못하게 하는 변경 사유와 기록.
- 범위 밖 변경과 기존 사용자 수정 보존 검사.
- 변경된 코드·검수보고·증거를 이전 통과로 인정하지 않는 지문 검사.
- 검증 완료와 실제 게시·배포·발송 권한의 구분. 이미 받은 승인을 반복해서 받으라는 의미로 쓰지 않는다.

관련 기존 테스트 5개 파일의 24개 테스트가 모두 통과했다(205 assertions). 이 테스트는 저장소 **0.10.0 소스**를 실행했으며, E2E의 설치 실행 파일 **0.9.1**과 구분한다. 여기에는 evidence 경로의 symlink 거부, 범위 이탈, 검수보고 변조, 코드 변경 후 audit 무효화, Git 지문에 결속된 audit에서 중복 명령 생략이 포함된다. **이 테스트는 해당 소스의 게이트가 설계대로 동작한다는 증거이며, Astra 작업 품질 향상 폭의 증거는 아니다.**

## 추가하면 좋은 지침

1. **사용자 의도와 승인 우선순위.** 일반 스킬 규칙보다 현재 사용자의 명시적 요구·기존 승인을 우선한다. 막힌 이유가 스킬이라면 정확한 파일·문구를 드러내고 이미 승인된 독립 작업은 계속한다.
2. **검증 종료 기준.** 변경과 관련된 의미 있는 검사를 통과했으면 새 변경·실패·남은 우려가 있을 때만 확대한다. CLI의 evidence 및 done 게이트를 생략하는 근거로 삼지 않는다.
3. **필요할 때만 읽는 참고 자료.** 루트 지침에는 목표·권한·검증 불변식과 라우팅만 남기고 provider/schema/오류 복구 예시는 실제 사용 지점으로 이동한다. 인계·stale 복구 과제를 별도로 넣어 참조 자료를 찾을 수 있는지도 검증한다.
4. **규칙별 수명 관리.** 각 의무 규칙에 발생한 실패, 적용 범위, 책임 주체(CLI/모델/사용자), 마지막 측정, 제거 조건을 기록한다. 모델이 바뀌면 해당 규칙의 A/B만 다시 실행한다.
5. **실패와 측정 오류 분리.** 테스트 실패는 품질 결과로 남기고, usage 누락·arm 오염·hidden 유출은 측정 오류로 별도 기록한다. 성공 run만 골라 속도를 비교하지 않는다.
6. **이미 있는 일괄 등록 사용.** 계획 문서에 검증 항목이 있는 경우 `gdm plan add --from-brief`를 안내한다(`cli/src/cli.ts:133`). 개별 add마다 모델 왕복을 만들 필요가 없다. 이 명령을 쓰기 위해 작은 작업에도 별도 계획 문서를 의무화하지 않는다. 효과는 이번 arm에 포함하지 않았다.

구현할 때는 설치본을 각각 수정하지 않고 `skills/_shared/work-protocol.md`, `skills/_shared/targets/codex.md`, `skills/_shared/targets/fragments/codex-delegation.md`, 각 source `SKILL.md`와 `install/render-skills.ts`를 함께 검토한다. 필요한 시점에 참조 파일을 실제로 찾고 읽을 수 있는지, 대상별 렌더 hash가 일관되는지도 확인해야 한다.

OpenAI의 [Astra 공식 가이드](https://developers.openai.com/api/docs/guides/latest-model)는 스킬·AGENTS의 충돌 점검, 불필요한 승인 중단 감소, 작업 크기에 맞는 검증, 업무에 맞는 위임 기준을 권고한다. 이는 이 저장소에서 실제 이득이 난다는 측정 결과를 대신하지 않는다. [모델 문서](https://developers.openai.com/api/docs/models/gpt-6-astra)의 공개 기능과 이번 CLI에서 요청한 모델 ID도 구분한다.

## 해석의 한계와 다음 비교

- 과제 3종은 기존에 사용한 작은 fixture다. 만점이 나와도 어려운 저장소 작업의 품질 비열등성이 입증된 것은 아니다.
- 모델 요청은 고정했지만 원격 서버의 실제 모델 identity를 독립적으로 증명하지 않는다.
- Astra만 실행했으므로 관측된 차이가 Astra 고유의 효과인지 이전 모델에서도 같은지는 판별하지 못한다.
- B는 상세 protocol과 웹/도메인 설명뿐 아니라 일반 CLI 실행 예시도 함께 분리했다. 일반 예시는 단일 로컬 구현에도 도움이 될 수 있다. C는 세 개의 절차 정책과 검증 종료 문구를 함께 바꿨다. 따라서 B의 결과를 protocol만의 효과로, C의 결과를 특정 한 조항의 효과로 보고하지 않는다.
- 숨긴 테스트는 prompt/workspace에서 제외했지만 OS 수준의 완전한 접근 차단 실험이 아니다. 외부 경로 접근과 다른 run 열람을 raw trace에서 확인해야 한다.
- 단계 2는 새 holdout 과제에 1줄 변경, cross-file 버그, 설계, 위험한 상태 전이, 환경 문제, 불완전한 audit 입력, 인계/재개, UI 검증을 포함한다. 정확도·탈출 결함을 먼저 보고 시간·토큰을 비교한다.
- 같은 모델 fresh-context audit vs 다른 모델, Astra 직접 설계 vs Claude 사전 설계, xhigh vs high는 각각 한 요인씩 독립 비교한다. UI·memory·Computer Use·Context Pack은 이 실험으로 제거 또는 기본 활성화하지 않는다.
