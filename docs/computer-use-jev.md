# Rust Computer Use와 Jev 실험

Computer Use는 GDM 네이티브 기능이다. Pi 호스트 어댑터와 표준 stdio MCP 서버가
같은 Rust 구현을 사용한다. 실제 입력 대상은 전용 macOS Tart VM이며 호스트 데스크톱을
조작하지 않는다. macOS Apple Silicon, 고정된 Tart/Softnet 빌드와 준비된 VM이 필요하다.

```sh
gdm computer-use setup --check  # 설치 조건 확인만 수행
gdm computer-use setup          # 명시적으로 전용 VM 준비
gdm computer-use mcp            # MCP 호스트가 실행하는 stdio 서버
```

설치 명령은 호스트의 Homebrew 설치나 관리자 권한 설정을 자동 실행하지 않는다.
필요한 경우 실행할 명령을 안내한다. 다른 프로세스가 실행 중인 VM에는 붙지 않는다.
종료 시 자신이 소유한 VM 프로세스만 회수한다.

## 후보 생성과 선택

```text
기존 비전 모델 → 화면 설명 + 구체적인 행동 후보
                         ↓
                 Jev → 후보 ID 또는 abstain
                         ↓
              Rust 검증 → 화면 재확인 → 실행
```

Jev는 화면 이미지를 직접 해석하지 않는다. 기존 모델이 작성한 화면 설명과 후보만
받는다. 후보는 최대 32개이고 VM 시작·종료 같은 수명 주기 작업은 제외한다.
응답 ID, 확률 분포와 신뢰도, 원본 후보·화면 해시를 검증한다. 신뢰도는 정확성이나
권한의 증명이 아니다. 현재 실험 임계값은 0.8이다.

- `gdm_computer_use`: 일반 화면 조회와 GUI 입력.
- `gdm_computer_choose`: Jev의 선택 결과만 반환. 입력은 실행하지 않는다.
- `gdm_computer_step`: 명시적으로 전달한 후보 중 하나를 선택하고 Rust 실행기가
  실행한 뒤 화면을 반환한다. 선택을 위해 모델을 한 번 더 호출하지 않는다.

기권, 알려지지 않은 후보, 통신 실패, 화면 변경은 실행하지 않는다.
픽셀 해시를 엄격하게 비교하므로 시계·커서 깜박임 같은 변화도 재선택을 요구할 수 있다.
이 기능은 기본 활성화된 가속 경로가 아니라 선택 가능한 실험 도구다.

## 자격 증명

`TYPESAFE_API_KEY` 환경변수 또는 명시적인 `--env-file`을 사용한다. dotenv의
`TYPESAFE_API_KEY=...` 형식과 키 하나만 있는 파일을 지원한다. 작업 폴더의 `.env`를
자동 탐색하지 않으며 키를 저장소·보고서에 복사하지 않는다.

```sh
gdm computer-use mcp --env-file /absolute/path/to/.env
```

Pi 어댑터에는 `GDM_TYPESAFE_ENV_FILE`로 파일 경로만 전달할 수 있다. MCP 호스트에는
실행 명령 `gdm`과 인자 `computer-use mcp --env-file <경로>`를 등록한다.
`gid`에서 자동으로 켜지는 설정 변경은 포함하지 않는다. 해당 엔진의 MCP 등록을 사용한다.

## 재현 가능한 실측

```sh
gdm computer-use benchmark --live-vm \
  --env-file /absolute/path/to/.env \
  --output /tmp/jev-results.json --model sonnet --repeats 3
```

공식 Claude CLI의 로그인 상태를 사용하며 도구를 끈다. 임시 폴더에서 합성 화면과
과제만 전달한다. 두 실험군 모두 같은 모델이 후보를 생성한다. 기준군은 같은 호출에서
선택도 수행하며, 실험군은 선택을 Jev에 맡긴다. 매 요청마다 새 CLI 프로세스를 실행하므로
지속 세션을 쓰는 gid의 지연 시간과 같다고 볼 수 없다.

실험은 전용 VM에 임시 TextEdit 파일 하나를 만들고 전체 화면으로 연다. 매 시도마다
`REPLACE ME`를 선택한 상태로 초기화한 뒤 정해진 문자열로 교체한다. 전체 화면은
시계·Dock 애니메이션을 가리며, 텍스트 선택은 커서 깜박임을 없앤다.
실제 입력 후 저장된 파일을 읽어 정확히 일치하는지 검증한다.
후보 생성, 선택, GUI 실행, 검증 시간과 실패를
분리해서 기록하고 실행 순서를 번갈아 배치한다. v2의 `end_to_end_ms`는 검증용 파일
조회 시간을 제외한 작업 지연이며 `attempt_wall_ms`는 검증까지 포함한다.
VM 부팅·실험 문서 준비는 두 군의 작업 시간에서 제외한다. 실패 시도도 집계에서 지우지 않는다.
`--diagnostic-frames`를 추가하면 화면 변경으로 중단된 시도의 전후 PNG를 결과 파일
옆에 저장한다. 기본값은 저장하지 않는다.

매번 후보를 다시 만들면 Jev API 왕복이 추가된다. 따라서 Jev의 선택 호출이 빨라도
전체 작업이 빨라진다는 뜻은 아니다. 후보 재사용이나 별도의 비싼 판단 호출을 대체하는
경우의 이득은 이 단일 행동 실험에서 증명되지 않는다. 결과 JSON과 해석은
`bench/computer-use-jev`에 보관한다.

이번 최종 3회 반복은 양쪽 모두 3/3 성공했고 전체 지연 중앙값은 기존 모델 9.155초,
Jev 추가 9.852초였다. 이 단순 과제에서는 가속 효과를 확인하지 못했다.
모델 버전은 [TypeSafe 모델 문서](https://docs.typesafe.ai/models)를 기준으로
`jev-1.13.0`에 고정했다.

## 후보 재사용 실험

```sh
cargo build --locked
python3 script/qa/rust-jev-reuse.py \
  --env-file /absolute/path/to/.env --repeats 5 \
  --output /tmp/jev-reuse-results.json
```

`computer-use benchmark-reuse --live-vm`은 기존 모델이 만든 후보를 네 번의 입력에
재사용하는 별도의 실험이다. 이름, 도시, 인원, 확인을 입력하는 Rust 폼을 전용 VM의
Terminal에 띄우고 실제 RFB 키 입력으로 수행한다. 기존 접근성 권한으로 TextEdit 상태를
읽을 수 없어, 권한을 변경하는 대신 상태를 제공하는 합성 폼을 사용했다.
이 폼은 입력을 데이터로만 처리하며 명령 실행이나 외부 전송을 하지 않는다.

세 비교군은 같은 목표, 화면, 상태 관측, 입력 제한과 실행 전 검사를 사용한다.

| 비교군 | 기존 모델의 역할 | Jev의 역할 |
|---|---|---|
| `model_each_step` | 매 단계 후보 생성과 한 행동 선택 | 없음 |
| `model_batch` | 한 번에 후보와 전체 실행 순서 생성 | 없음 |
| `model_reuse_jev` | 한 번에 후보 생성 | 매 단계 현재 상태에 맞는 후보 선택 |

기존 모델의 일괄 계획을 함께 측정해야 모델 호출을 줄인 이득과 Jev 자체의 이득을
구분할 수 있다. 실행 순서를 회차마다 순환시키고 실패도 삭제하지 않는다. 작업 시간에는
모델 호출, Jev 선택, 매 단계 상태 조회, 화면 검증, 실제 입력과 후보 재생성을 포함한다.
VM 준비, 폼 초기화, 마지막 상태 파일의 별도 검증은 제외하고 검증 시간은 따로 기록한다.
새 모델 CLI 프로세스마다 발생하는 지연도 포함한다.

폼에는 단계별 색상 표식이 있다. 실제 화면에 현재 단계의 표식이 나타나고 연속 두
화면이 같아야 모델에 관측을 전달한다. 초기화 직후 직전 작업의 화면이 전달되던 문제를
막기 위해 초기화도 폼의 입력 경로로 실행한다. 모델을 호출하지 않고 초기화와 여덟 번의 입력을 확인하려면 같은
CLI에 `--fixture-check`를 추가한다. 표식은 실험 폼의 관측에만 사용한다.

후보 캐시는 폼의 실행 ID, 현재 단계와 값, 마지막으로 확인한 화면에 결속된다. 현재
상태만 새로 반영하고 후보의 행동은 바꾸지 않는다. 선택 뒤 상태와 전체 화면 해시를
다시 확인한 다음에만 입력하며, 실행 결과가 해당 입력과 일치해야 캐시를 다음 단계로
옮긴다. 다른 전면 앱이나 프로세스, 변조된 후보, 여러 줄 입력, 키보드 단축키는 거부한다.
후보의 입력 문자열도 해당 합성 과제에 명시된 네 값으로 제한한다.
행동의 내용은 모델이 만들고, 후보의 안정적인 ID는 Rust가 배열 순서에 따라 부여한다.
기존 모델의 직접 선택은 배열 번호로 받아 범위를 검증하고, Jev의 선택은 해당 ID와
후보 해시에 결속한다. 모델이 ID를 다른 표기로 복사하는 오류를 실행에 전달하지 않는다.

기권, 화면 불일치, 180초 만료 시에는 먼저 실행을 중단한다. 같은 폼과 전면 프로세스가
유지되는 경우 최신 관측으로 기존 모델에 후보 재생성을 최대 한 번 요청한다. 추가
호출과 실패도 결과에 남기며 무제한 재시도하지 않는다. 폼이나 프로세스가 바뀌면 중단한다.

이 경로는 **통제된 폼 실험 전용**이며 MCP나 gid의 기본 실행 경로에 연결하지 않았다.
임의의 앱에서는 안전한 상태 관측과 대상 결속을 제공하는 어댑터가 별도로 필요하다.
기존 `gdm_computer_step`의 한 화면에 대한 엄격한 검사도 유지한다.

5회씩 실측한 결과 모델 호출은 작업당 4회에서 1회로 줄었다. 성공한 작업의 지연
중앙값은 단계별 모델 82.7초, 일괄 계획 63.1초, Jev 재사용 70.7초였다. 성공 횟수는
각각 5/5, 4/5, 4/5이며 두 실패는 화면 동기화 시간 초과였다. 따라서 Jev의 속도
우위는 확정하지 않는다. [전체 결과와 한계](../bench/computer-use-jev/README.md)에
실패를 포함한 측정과 재현 방법을 기록했다.

Rust 코드에서는 `reuse.rs`의 `Cache`가 변경 불가능한 후보를 소유한다. `bind()`는
후보를 복사해 현재 관측에 연결하고, `advance()`만 검증된 상태 전이를 반영한다.
이렇게 소유권과 상태 변경 지점을 제한하면 어떤 행동을 어느 화면에서 허용했는지
추적하고 테스트하기 쉽다.
